# API SchoolHub

Базовый URL: `/api/v1` · Интерактивная документация: **`/docs`** (Swagger UI) и `/openapi.json`.

В таблице доступа: **В** = Владелец, **А** = Администрация, **У** = Учитель.
`—` означает, что запрос будет отклонён с `403`.

---

## 0. Первоначальная настройка

До создания первого Владельца **весь API закрыт** (`503 SETUP_REQUIRED`), кроме
`/health` и `/setup/*` — приложение невозможно использовать «вслепую», но и
посторонний не может назначить себя администратором: нужен одноразовый код из
журнала контейнера.

| Метод | Путь | Доступ | Назначение |
|---|---|---|---|
| `GET` | `/setup/status` | 🔓 | Требуется ли настройка; название школы; кто завершил настройку |
| `POST` | `/setup/first-owner` | 🔓 + код | Создать первого Владельца |
| `POST` | `/setup/token` | только `localhost` | Показать код повторно (со внешнего адреса — `403`) |
| `GET` | `/setup/info` | 🔓 | Режим работы: `app_env`, источник `SECRET_KEY`, включён ли LDAP |
| `GET` | `/health` | 🔓 | Healthcheck |

**Запрос** `POST /setup/first-owner`

```json
{
  "setup_token": "VW88DT6V",
  "email": "admin@school.local",
  "password": "Школа2026!",
  "full_name": "Соколова Ирина Аркадьевна",
  "school_name": "ГБОУ Школа № 1472"
}
```

**Ответ 201** — карточка созданного Владельца (`role: "OWNER"`, `auth_source: "local"`),
после чего API немедленно разблокируется. Ошибки: `403` — неверный код/слабые данные,
`409` — система уже настроена (настройка выполняется один раз), `422` — пароль короче 8 символов.

Код настройки генерируется при первом старте (8 символов без неоднозначных знаков) и
печатается в журнал контейнера. Альтернатива без браузера:

```bash
docker exec -it schoolhub-backend python -m scripts.first_owner     --email admin@school.local --password 'Пароль12345' --name 'Администратор школы'
```

## 1. Аутентификация

| Метод | Путь | В | А | У | Назначение |
|---|---|:--:|:--:|:--:|---|
| `POST` | `/auth/login` | ✅ | ✅ | ✅ | Вход: **e-mail или доменная учётка** + пароль → access в теле, refresh в httpOnly-cookie |
| `GET` | `/auth/login-options` | 🔓 | 🔓 | 🔓 | Публично: включён ли вход через домен, подсказка о формате логина |
| `GET` | `/auth/ad/diagnostics` | ✅ | ✅ | — | Диагностика подключения к AD (конфиг без секретов + ping DC) |
| `POST` | `/auth/refresh` | ✅ | ✅ | ✅ | Обмен refresh-cookie на новый access **с ротацией** refresh |
| `GET` | `/auth/me` | ✅ | ✅ | ✅ | Профиль + `capabilities` (права для UI) |
| `POST` | `/auth/change-password` | ✅ | ✅ | ✅ | Смена пароля **локальной** учётки (для доменных — `403`); отзывает все сессии |
| `POST` | `/auth/logout` | ✅ | ✅ | ✅ | Выход: **отзыв refresh-сессии** на сервере + удаление cookie + запись в журнале |

**Запрос** `POST /auth/login`

```json
{ "email": "owner@schoolhub.ru", "password": "Demo1234!", "remember": true }
```

`remember: true` (по умолчанию) — refresh-cookie живёт 14 дней (`Max-Age`);
`false` — cookie сессионная и умирает при закрытии браузера.

Поле `email` принимает и **доменный логин** (если включена интеграция с AD):
`ivanov`, `ivanov@school.local`, `SCHOOL\ivanov`. Значение проходит строгую
валидацию набора символов и дополнительно экранируется перед попаданием в LDAP-фильтр.

**Ответ `GET /auth/login-options`** (без авторизации — используется экраном входа):

```json
{
  "ldap_enabled": true,
  "local_enabled": true,
  "login_hint": "Доменная учётная запись: ivanov или ivanov@school.local",
  "password_managed_by": "Active Directory"
}
```

**Ответ `GET /auth/ad/diagnostics`** (OWNER/ADMIN):

```json
{
  "config": { "server": "dc01.school.local:636", "ssl": true, "base_dn": "DC=school,DC=local",
              "bind_dn": "CN=svc_schoolhub,…", "bind_password_set": true,
              "allowed_groups": ["SchoolStaff"], "admin_groups": ["SchoolAdmins"], "…": "…" },
  "problems": ["Не задан LDAP_CA_CERT — сертификат DC не будет проверен"],
  "ping": { "ok": true, "server": "dc01.school.local:636" },
  "requested_by": "admin@school.local"
}
```

Значение пароля сервисной учётки в ответ **не попадает** — только признак `bind_password_set`.

**Ответ 200** (refresh-токен в теле **не отдаётся** — он приходит в `Set-Cookie`)

```json
{ "access_token": "eyJhbGciOiJIUzI1NiIs…", "token_type": "bearer", "expires_in": 1800 }
```

```
Set-Cookie: schoolhub_refresh=eyJhbGci…; HttpOnly; Max-Age=1209600; Path=/api/v1/auth; SameSite=strict
```

`Secure` добавляется при `COOKIE_SECURE=true` (работа по HTTPS). `Path=/api/v1/auth`
ограничивает круг эндпоинтов, которым браузер отправляет cookie.

**Ответ `GET /auth/me`**

```json
{
  "id": "8b1c…", "email": "ivanov@schoolhub.ru",
  "full_name": "Иванов Пётр Сергеевич", "position": "Учитель математики",
  "role": "TEACHER", "is_active": true,
  "capabilities": ["orders:read", "orders:ack", "tasks:read-own", "plans:read"]
}
```

Токены: access — 30 минут (в SPA живёт только в памяти вкладки), refresh — 14 дней
(httpOnly-cookie); различаются claim'ом `typ`, каждый имеет `jti`.
Заголовок авторизации: `Authorization: Bearer <access_token>`.

Ошибки: `401` — неверная пара или истёк токен (сообщение одинаковое для «нет такого e-mail»
и «неверный пароль»), `403` — учётная запись заблокирована.

### Refresh-сессии: ротация и отзыв (v1.3)

Каждый выданный refresh-токен — строка `refresh_sessions` (`jti` уникален, `family_id`
объединяет токены одного входа). Правила:

* `POST /auth/refresh` **ротирует** токен: предъявленный `jti` помечается `superseded_at`,
  в ответе приходит новый access и новая cookie;
* предъявление уже заменённого токена **вне льготного окна** (`REFRESH_REUSE_GRACE_SEC`,
  по умолчанию 30 с — запас для гонок параллельных вкладок) трактуется как кража:
  всё семейство отзывается, в журнал пишется `TOKEN_REUSE_DETECTED`, ответ `401`;
* `POST /auth/logout` отзывает семейство предъявленной cookie;
* смена собственного пароля, сброс пароля администрацией и блокировка учётки
  отзывают **все** refresh-сессии пользователя (`revocation_reason` фиксирует причину);
* заблокированный пользователь дополнительно получает `403` на любой запрос с валидным
  access-токеном — `is_active` проверяется на каждом запросе.

Ошибки refresh: `401` — cookie отсутствует, токен неизвестен/отозван/истёк/ротация
скомпрометирована; ответ всегда без подробностей, пригодных для перечисления.

| `POST` | `/orders` | ✅ | ✅ | — | Создать черновик (`require_all` либо `recipient_ids`) |

| `POST` | `/orders/{id}/files` | ✅ | ✅ | — | Загрузить PDF/DOCX (новая версия) |
| `DELETE` | `/orders/{id}/files/{file_id}` | ✅ | ✅ | — | Удалить файл черновика |

| `GET` | `/orders/{id}/acknowledgements` | ✅ | ✅ | — | Лист ознакомления |
| `GET` | `/orders/{id}/ack-summary` | ✅ | ✅ | — | Прогресс + список неподписавших |

¹ Учитель видит только приказы в статусе `PUBLISHED`; запрос черновика/архива → `403`,
фильтр `status` для учителя отклоняется с `403`.

**Круг ознакомления** задаётся ещё в черновике: `require_all: true` (все активные сотрудники,
кроме Владельца) либо `require_all: false` + `recipient_ids: [uuid…]` (сохраняется на приказе
и применяется при публикации). После публикации круг меняется через `PUT /{id}/recipients`:
добавленные получают уведомление и строку «Не ознакомлен», неподписавшие убираются из листа,
уже подтверждённые подписи сохраняются. Подтверждение ознакомления сотрудником вне круга → `409`.

### Политика подписи приказа (ПЭП)

У каждого приказа есть поле `signature_policy` — требуемый уровень электронной подписи
ознакомления:

| Значение | Смысл | Что требуется при подписании |
|---|---|---|
| `NONE` | без подписи (аудит) | ничего — факт фиксируется временем и в журнале событий |
| `CLICK` | клик «Ознакомлен» (по умолчанию) | ничего сверх учётной записи |
| `TOTP` | усиленная: код из аутентификатора | одноразовый 6-значный код (`code`) |
| `CODE_WORD` | максимальная: код + контрольное слово | `code` **и** `word` |

Политика задаётся при создании/редактировании приказа полем `signature_policy`
(в веб-форме — селектор «Подпись ознакомления», v1.11+). **Автоправило «тип приказа →
политика»** работает поверх выбора: приказы о движении обучающихся
(`order_type=STUDENTS`) не могут получить политику ниже `TOTP` — запрошенная более
слабая политика автоматически повышается сервером до усиленной; для остальных типов
по умолчанию — `CLICK`.

В ответах `/orders*` присутствуют поля `signature_policy` (объявленная политика) и
`my_ack.sign_method` (фактический способ подписи). В листе ознакомления и CSV-выгрузке
`/orders/export/ack-sheet.csv` каждая строка содержит **способ подписи и время**.

### Подтверждение ознакомления

`POST /orders/{id}/acknowledgements`

```json
{
  "comment": "Ознакомлен, принято к исполнению",
  "code": "492817",                       // обязателен при политике TOTP/CODE_WORD
  "word": "багульник"                     // обязателен при политике CODE_WORD
}
```

Ответ `200` — запись листа ознакомления со служебными полями:

```json
{
  "id": "…", "status": "ACKNOWLEDGED",
  "acknowledged_at": "2026-10-12T08:15:03.112155Z",
  "sign_method": "TOTP",                  // NONE/CLICK/TOTP/CODE_WORD
  "comment": "Ознакомлен, принято к исполнению",
  "ip_address": "10.0.12.34",
  "user": { "id": "…", "email": "ivanov@schoolhub.ru", "full_name": "Иванов Пётр Сергеевич" }
}
```

Ошибки: `409` — уже подтверждено ранее, приказ в архиве, сотрудник не входит в круг
ознакомления, либо документ требует код, а аутентификатор не привязан
(`code: "TOTP_NOT_BOUND"` с подсказкой «привяжите аутентификатор в профиле»;
**фолбэка на пароль нет**); `422` — неверный/просроченный код (`TOTP_INVALID_CODE`)
или несовпавшее контрольное слово (`RECOVERY_WORD_MISMATCH`); `403` — приказ не
опубликован (для учителя).

### Загрузка документа

`POST /orders/{id}/files` — `multipart/form-data`, поле `file`.

Ограничения: `application/pdf`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document`,
`application/msword`; до 25 МБ; пустой файл отклоняется. Каждый вызов создаёт **новую версию**
(`version`, `is_current`), предыдущие сохраняются вместе с sha256.

```bash
curl -X POST http://localhost:8000/api/v1/orders/$ORDER_ID/files \
  -H "Authorization: Bearer $TOKEN" \
  -F "file=@prikaz.pdf;type=application/pdf"
```

### Жизненный цикл приказа

```
DRAFT ──publish──► PUBLISHED ──archive──► ARCHIVED
   │                    │
   └──delete (можно)    └── редактирование и новые версии файла (можно)
```

* публикация без загруженного документа → `409`;
* архивный приказ нельзя редактировать, догружать файлы и собирать подписи → `409`;
* удалить можно только черновик, опубликованный приказ — только в архив (требование к archivability).

### Отметки «выполнено» (несколько исполнителей)

У задачи может быть несколько исполнителей (`assignee_ids`), у каждого — своя отметка
(`task_assignees.done_at`). Автоматика статусов:

* первая отметка (задача `NEW`) → `IN_PROGRESS`;
* отметки поставили **все** исполнители → `DONE` (`completed_at` заполняется, постановщик
  получает уведомление «все исполнители отметились»);
* снятие отметки у закрытой задачи → `IN_PROGRESS` (`completed_at` очищается).

Администрация по-прежнему может менять статус вручную (state machine) — включая досрочное
закрытие задачи. Ответ элемента списка содержит `assignees[]` (с `done_at` каждого),
`marks_done`, `can_mark`, `my_done`, `files_count`.

| `NEW` | ✅ | Новая |
| `IN_PROGRESS` | ✅ | В работе |
| `DONE` | ✅ | Выполнена (`completed_at` заполняется автоматически) |
| `OVERDUE` | ⛔ вычисляется | `status != DONE AND deadline < now()` — отдаётся в `effective_status` |

Разрешённые переходы: `NEW → IN_PROGRESS | DONE`, `IN_PROGRESS → DONE | NEW`, `DONE → IN_PROGRESS`.
Прочие переходы → `409`. Просроченная задача остаётся в своём хранимом статусе, но в ответах
приходит `effective_status: "OVERDUE"`, `is_overdue: true`, `days_left: -2`.

### Пример ответа элемента списка

```json
{
  "id": "…", "title": "Подготовить кабинет №12 к проверке",
  "status": "NEW", "effective_status": "OVERDUE", "priority": "URGENT",
  "deadline": "2026-10-11T14:00:00Z", "is_overdue": true, "days_left": -1,
  "assignees": [
    { "id": "…", "done_at": null, "user": { "id": "…", "full_name": "Иванов Пётр Сергеевич", "role": "TEACHER" } },
    { "id": "…", "done_at": null, "user": { "id": "…", "full_name": "Смирнов Алексей Игоревич", "role": "TEACHER" } }
  ],
  "marks_done": 0, "my_done": false, "can_mark": true, "files_count": 1,
  "creator": { "id": "…", "full_name": "Гаврилов Сергей Николаевич", "role": "ADMIN" },

```

### Повторяющиеся задачи и история повторов (v1.10)

У задачи может быть периодичность: `recurrence` = `NONE` | `DAILY` | `WEEKLY`
(+ `recurrence_weekdays`, дни ISO 1=пн…7=вс) | `MONTHLY` (+ `recurrence_day`,
1–31 с переносом на последний день коротких месяцев). У повторяющейся задачи
нет разового дедлайна (`deadline = null`): срок задаёт период, а `OVERDUE` для
неё не вычисляется. Одна строка в БД: к началу нового периода выполненная задача
автоматически возвращается в `NEW` (отметки исполнителей очищаются,
`last_done_at` сохраняется).

С 1.10.0 каждый **закрытый** период фиксируется в истории повторов
(`task_occurrences`): период выполнен (`DONE` — кто и когда закрыл) или провален
(`MISSED` — период истёк, задачу не выполнили). Ответы задач дополнены полями:

| Поле | Тип | Смысл |
|---|---|---|
| `missed_streak` | int | сколько периодов подряд провалено (0 — последний закрытый период выполнен) |
| `last_occurrence_start` | date | начало последнего закрытого периода (`ГГГГ-ММ-ДД`, локальная дата) |
| `last_occurrence_status` | string | `DONE` / `MISSED` / `null` — чем закрыт последний период |

`GET /tasks/{id}/occurrences?limit=60` (1–365) — массив закрытых периодов,
новые первыми:

```json
[
  {
    "period_start": "2026-10-28",
    "status": "DONE",
    "completed_at": "2026-10-28T12:31:05Z",
    "completed_by": ["Иванов Пётр Сергеевич"],
    "closed_at": "2026-10-28T12:31:05Z"
  },
  {
    "period_start": "2026-10-27",
    "status": "MISSED",
    "completed_at": null,
    "completed_by": [],
    "closed_at": "2026-10-28T00:05:11Z"
  }
]
```

Тонкости:

* отсчёт истории начинается с момента включения v1.10.0: периоды ДО обновления
  задним числом не проваливаются;
* снятие отметки «выполнено» (или перевод задачи из `DONE`) снова открывает
  текущий период — запись `DONE` за него откатывается;
* проваленные периоды закрывает фоновый `rollover_due` (ежечасно и при каждом
  чтении списка/карточки задач), поэтому «вчера пропущено» становится видно
  не позднее начала следующего периода.

## 4. План работы на неделю

(`month_items`, `week_items`), мероприятия по дням пн–сб (`days[].events[]`).
Ответственные (`resp`, `duty.teacher_id`) — UUID сотрудников, в ответах отдаются карточками `User`.

| `GET` | `/plans/{id}` | ✅ | ✅ | ✅⁶ | Документ целиком (+ `events_total`, `my_items`) |
| `PATCH` | `/plans/{id}` | ✅ | ✅ | — | Изменить (не архив); можно перенести неделю |
| `POST` | `/plans/{id}/publish` | ✅ | ✅ | — | Опубликовать: уведомление всем ответственным |
| `POST` | `/plans/{id}/archive` | ✅ | ✅ | — | В архив (read-only) |
| `DELETE` | `/plans/{id}` | ✅ | ✅ | — | Удалить **черновик** |

| Метод | Путь | В | А | У | Назначение |
|---|---|:--:|:--:|:--:|---|
| `GET` | `/users` | ✅ все | ✅ без Владельца | — | Список с поиском и фильтром по роли |
| `GET` | `/users/options` | ✅ | ✅ | — | Компактный список для селектов (исполнители) |
| `GET` | `/users/{id}` | ✅ | ✅ (не Владельца) | — | Карточка |
| `POST` | `/users` | ✅ любая роль | ⚠️ только `TEACHER` | — | Создать учётную запись |
| `PATCH` | `/users/{id}` | ✅ | ⚠️ только Учителя | — | Изменить данные/роль/активность/пароль |
| `DELETE` | `/users/{id}` | ✅ | — | — | Заблокировать (мягкое удаление) |
| `GET` | `/users/ad/search?q=` | ✅ | ✅ | — | Поиск пользователей в каталоге домена |
| `POST` | `/users/ad/import` | ✅ | ⚠️ роль ≤ своей | — | Импорт учётных записей из AD (до их первого входа) |

**Персональные гранты доступа** (поля `PATCH /users/{id}` и `POST /users/bulk-update`,
правит только Владелец): `incoming_journal_access`, `movement_access`,
`equipment_access` и — с v1.11 — `notes_full_access` («Все служебные записки»:
сотрудник видит весь журнал записок, как Владелец; по умолчанию каждый видит только
свои) и `substitutions_access` («Кадровик»: журнал замещений целиком + удаление строк
замещений; должность значения не имеет). Гранты приходят в ответах `/users*` и
`/auth/me` и добавляют соответствующие capability (`movement:read`, `equipment:read`,
`substitutions:read`).

**Поля доменной интеграции** в ответах `/users*` и `/auth/me`:
`auth_source` (`local` / `ldap`), `domain_account` (sAMAccountName), `ad_groups`
(список групп AD), `last_ad_sync_at`.

**Запрос** `POST /users/ad/import`

```json
{ "usernames": ["zavuch", "ivanov"], "role": "ADMIN" }
```

**Ответ 200**

```json
{ "created": ["zavuch@school.local"], "skipped": ["ivanov"], "failed": [], "total": 1 }
```

Гарантии целостности:

* свою роль и свою активность изменить нельзя (`409`);
* в школе всегда остаётся хотя бы один активный Владелец (`409`);
* Администрация не может выдать роль `ADMIN`/`OWNER` и не видит учётку Владельца (`403`);
* e-mail уникален (`409` при дубликате); пароль — от 8 символов;
* для учётки с `auth_source=ldap` смена/установка пароля невозможна (`409`) — им управляет AD;
* импорт из AD идемпотентен: существующие учётки попадают в `skipped`, дубли внутри
  одного запроса игнорируются; роль выше собственной назначить нельзя (`403`);
* **удаление пользователя (мягкое) требует подпись «код + слово»** (см. § 5.1).

### 5.1 Электронная подпись: привязка аутентификатора (TOTP)

Раздел профиля каждого сотрудника. Секрет выдаётся **одноразово** и больше никогда
не возвращается API; привязка считается завершённой только после подтверждения
первым кодом из приложения.

| Метод | Путь | В | А | У | Назначение |
|---|---|:--:|:--:|:--:|---|
| `POST` | `/users/me/totp/setup` | ✅ | ✅ | ✅ | Начать привязку: `{secret, otpauth_uri}` (секрет — только в этом ответе) |
| `POST` | `/users/me/totp/confirm` | ✅ | ✅ | ✅ | Подтвердить привязку первым кодом (`204`); до этого `totp_enabled=false` |
| `DELETE` | `/users/me/totp` | ✅ | ✅ | ✅ | Отвязать аутентификатор: секрет уничтожается (`204`). **Действующая привязка снимается только текущим кодом** (`{"code": "123456"}`): без кода — `409 TOTP_CODE_REQUIRED`, неверный код — `422`. Незавершённую привязку можно снять без кода. `400`, если аутентификатор не привязан |
| `PUT` | `/users/me/totp/recovery-word` | ✅ | ✅ | ✅ | Установить контрольное слово для уровня «код + слово» (`{word, code}`, `204`) |
| `POST` | `/users/{user_id}/totp-reset` | — | — | 👑 | Аварийный сброс чужой привязки (сотрудник потерял телефон): ПЭП «код + слово» Владельца, `204`. `409`, если привязки нет. Сотрудник получает уведомление `TOTP_RESET` |
| `POST` | `/users/me/totp/break-glass` | 👑 | — | — | **Резервный сброс собственной привязки Владельца** без телефона: локальный пароль + контрольное слово (`204`). См. ниже |

В `/auth/me` добавлены поля `totp_enabled` (привязка подтверждена) и
`recovery_word_set_at`. В карточке сотрудника (`GET /users`, `GET /users/{id}`)
есть `totp_enabled` — по нему Владелец видит, кому доступен сброс. Все действия
фиксируются в журнале событий (`TOTP_SETUP_START`, `TOTP_CONFIRMED`,
`TOTP_REMOVED`, `TOTP_WORD_SET`, `TOTP_RESET`).

Подбор кода и контрольного слова ограничен: `TOTP_MAX_ATTEMPTS` неудач (по умолчанию 5)
за `TOTP_LOCK_WINDOW_MIN` минут (15) на человека — дальше `429 RATE_LIMITED`;
каждая неудача пишется в журнал отдельной транзакцией (`SIGNATURE_FAILED`).
Успешная подпись сбрасывает счётчик.

**Резервный сброс Владельца (`break-glass`, v1.12).** Штатный сброс чужой привязки
подписывает Владелец кодом TOTP; если устройство потерял сам Владелец, подписывать
нечем — а восстановлением из копии, выходом из локдауна и удалением учётных записей
управляет именно подпись. Без этой процедуры доступ возвращался только правкой базы
на NAS вручную. Подпись заменяется парой факторов, которые Владелец знает:
локальный пароль (bcrypt) и контрольное слово, заданное **заранее** и хранящееся
зашифрованным вместе с секретом.

```json
{ "password": "Школа2026!", "word": "тайное-слово" }
```

Доступен только Владельцу (`403` для администрации и учителей). Ошибки:
`409 RECOVERY_WORD_MISSING` — слово не задано (сбрасывать нечем, сначала
`PUT /users/me/totp/recovery-word`); `422 BREAK_GLASS_FAILED` — неверный пароль
или слово; `429 RATE_LIMITED` — исчерпан лимит. Подбор троттлится **отдельным**
лимитером, не общим со входом: `BREAK_GLASS_MAX_ATTEMPTS` (5) неудач за
`BREAK_GLASS_WINDOW_MIN` (30) минут. Каждая неудача пишется в журнал отдельной
транзакцией (`SIGNATURE_FAILED` с причиной в `changes.reason`), успех —
`TOTP_BREAK_GLASS_DONE`.

После успеха **отзываются все сессии Владельца**, включая текущую, а cookie
снимается в том же ответе — клиент обязан вернуть пользователя на экран входа.
Уведомление уходит Владельцу и всей администрации: снятие подписи с самой
привилегированной учётной записи должно быть видно не только тому, кто его сделал.

**Чувствительные операции требуют максимальный уровень «код + слово»**
(`code` + `word` в теле запроса): удаление пользователя (`DELETE /users/{id}`),
восстановление БД из копии (`POST /system/restore`), восстановление файлов из ZIP
(`POST /system/files-restore`), очистка журнала событий (`DELETE /audit`),
включение/выключение локдауна (`POST /system/lockdown`).

Ошибки подписи (единые для всех операций): `409 TOTP_NOT_BOUND` — аутентификатор
не привязан или код не передан (текст содержит подсказку, что сделать; **паролем
заменить нельзя**); `422 TOTP_INVALID_CODE` — неверный/просроченный код;
`409 RECOVERY_WORD_MISSING` — не задано контрольное слово; `422 RECOVERY_WORD_MISMATCH` —
слово не совпало.

## 6. Служебные записки

Записка пишется как задача: автор, тема, текст, вложения, исполнитель, срок
и **согласующий** (`approver_id` — выбирается из администрации; v1.11+).
Утверждение **всегда** требует подпись кодом из аутентификатора (уровень «код + слово»,
если у согласующего задано контрольное слово); утвердить может назначенный
согласующий или Владелец (`403` — иначе).

| Метод | Путь | В | А | У | Назначение |
|---|---|:--:|:--:|:--:|---|
| `POST` | `/notes` | ✅ | ✅ | ✅ | Создать черновик (`subject`, `body`, `executor_id`, `approver_id`, `deadline`) |
| `GET` | `/notes` | ✅¹ | ✅¹ | ✅ | Журнал с фильтрами (`status`, `author_id`, `executor_id`, период) |
| `GET` | `/notes/export.csv` | ✅¹ | ✅¹ | ✅ | Экспорт журнала в CSV (в пределах видимости) |
| `PATCH` | `/notes/{id}` | ✅ | ✅ | —² | Править черновик (только автор) |
| `POST` | `/notes/{id}/submit` | ✅ | ✅ | —² | Отправить на согласование |
| `POST` | `/notes/{id}/approve` | — | ✅³ | ✅ | Утвердить (**подпись кодом**) → автоматически создаётся задача исполнителю |
| `POST` | `/notes/{id}/reject` | — | ✅³ | ✅ | Отклонить → возврат автору с обязательным комментарием |
| `DELETE` | `/notes/{id}` | ✅⁴ | — | ✅⁴ | Удалить записку (204); задача от утверждённой записки остаётся |
| `POST` | `/notes/{id}/files` | ✅ | ✅ | —² | Прикрепить вложение |
| `GET` | `/notes/{id}/files/{file_id}/download` | ✅ | ✅ | ✅¹ | Скачать вложение |
| `DELETE` | `/notes/{id}/files/{file_id}` | ✅ | ✅ | —² | Удалить вложение |
| `GET` | `/notes/{id}/print?auto_print=` | ✅ | ✅ | — | Печатный бланк А4 (v1.12): шапка школы, адресат, номер и дата, тема, текст, приложения, реквизиты, подпись автора, виза «СОГЛАСОВАНО» со способом подписи и местом для печати, отметка об исполнении. `auto_print=true` сразу открывает диалог печати |

¹ **Видимость (v1.11)**: каждый сотрудник (включая администрацию) видит только
записки, где он автор, исполнитель или согласующий; Владелец и сотрудники с грантом
`notes_full_access` — весь журнал. Записки **без назначенного согласующего** видны
всей администрации (входящий пул на утверждение). Те же правила применяет глобальный
`GET /search`. Чужая записка — `404/403`, в поиске не появляется.
² По правам автора черновика. ³ Назначенный согласующий (`approver_id`) или Владелец.
⁴ Владелец (и сотрудник с грантом `notes_full_access`) удаляет записку в любом
статусе, включая утверждённую; автор — только свой черновик или отклонённую (`409`).
Удаление пишется в аудит (`NOTE_DELETE`).

Ответы `/notes*` содержат `approver_id` и `approver` (ФИО согласующего), а после
утверждения — визу `approved_at` / `approved_sign_method`; в веб-журнале и печатной
форме видно, **кто согласовал**.

**Вложения (v1.12).** У каждого файла служебной записки есть автоматически созданная
PDF-копия — `pdf_status` (`NA`/`PENDING`/`READY`/`FAILED`), `pdf_note` (причина, если
не получилось) и `pdf_ready`. `GET /notes/{id}/files/{file_id}/download?inline=true`
отдаёт копию, когда она готова, и оригинал — когда нет; без `inline` всегда отдаётся
оригинал. Копия не заменяет файл: Word-документ остаётся Word-документом.
При утверждении записки документы **дублируются** в созданную задачу
(`storage.duplicate` + копия PDF) — жизненные циклы записки и задачи независимы,
поэтому удаление файла из одной не ломает другую; число переданных вложений пишется
в историю задачи. Редактировать вложения может только автор и только в статусах
`DRAFT`/`REJECTED`.

**State machine**: `DRAFT → ON_APPROVAL → APPROVED → COMPLETED`; из `ON_APPROVAL`
возможен `REJECTED` (возврат в `DRAFT` автору с комментарием). Переходы вне таблицы —
`409`. После утверждения записка получает номер, ссылку на созданную задачу
(`task_id`) и визу (`approved_at`, `approved_sign_method`); у задачи обратная ссылка на
записку — ссылки взаимные. Закрытие задачи переводит записку в `COMPLETED`.

Типичный цикл:

```bash
# автор-учитель пишет записку и отправляет на согласование
```

## 7. Замещения

Администрация оформляет: отсутствующий сотрудник → замещающий, причина, период.
Флаги `transfer_tasks` / `transfer_plans` / `transfer_vshk` передают соответствующие
объекты замещающему: выполняется переназначение с записью в историю (аудит) и
уведомлениями обеим сторонам.

| Метод | Путь | В | А | У | Назначение |
|---|---|:--:|:--:|:--:|---|
| `POST` | `/substitutions` | ✅ | ✅ | — | Создать замещение (`absent_user_id`, `substitute_user_id`, `reason`, `start_date`, `end_date`, флаги передачи) — объекты при этом НЕ трогаются |
| `GET` | `/substitutions` | ✅¹ | ✅ | — | Журнал (фильтры `status`, `user_id`, `ongoing`) |
| `GET` | `/substitutions/export.csv` | — | ✅ | — | Экспорт журнала для отчётности |
| `POST` | `/substitutions/{id}/confirm` | — | — | ✅² | **Замещающий подтверждает простым кликом** — и только тогда объекты передаются |
| `POST` | `/substitutions/{id}/extend` | ✅ | ✅ | — | Продлить период: `{"end_date": "...", "comment": "..."}` (больничный продлили) |
| `POST` | `/substitutions/{id}/end` | ✅ | ✅ | — | Завершить замещение → объекты возвращаются отсутствующему |
| `POST` | `/substitutions/{id}/cancel` | ✅ | ✅ | — | Отменить (с комментарием) → объекты возвращаются отсутствующему |
| `DELETE` | `/substitutions/{id}` | ✅³ | ✅³ | — | Удалить строку журнала (204); живое замещение сначала возвращает объекты |

¹ Весь журнал видят Владелец, администрация и **кадровик** (грант Владельца
`users.substitutions_access`); сотруднику без гранта возвращаются только замещения,
в которых он участвует (иначе он не смог бы подтвердить принятие). CSV-экспорт
сотруднику — `403`. Capability `substitutions:read` выдаётся в `/auth/me`
администрации, кадровику и участнику активного замещения (пункт меню у учителя
появляется ровно на время его замещения).
² Только указанный замещающий сотрудник; подтверждение — без подписи, одним кликом.
³ Только Владелец и кадровик; администрация без гранта может отменить/завершить,
но не удалять строки.

**Жизненный цикл объектов (v1.11).** Флаги `transfer_tasks` / `transfer_plans` /
`transfer_vshk` описывают намерение; фактическая передача происходит в `confirm`
и отмечается полем `transferred_at` в ответе. Возврат отсутствующему выполняется при
`cancel`, `end`, `DELETE` и автоматически по истечении периода (`auto_expire`):
возвращаются только незакрытые задачи и только те ссылки ответственных, где сейчас
указан замещающий. Сводка передачи и возврата пишется в `note`, в историю задачи,
в уведомления обоих участников и в аудит (`SUBSTITUTION_CONFIRM` / `_END` / `_CANCEL`
/ `_EXTEND` / `_DELETE`).

Статусы: `ACTIVE → CONFIRMED → ENDED`, `CANCELLED` — отмена.

**Запрос** `POST /substitutions/{id}/extend`

```json
{ "end_date": "2026-11-12T00:00:00Z", "comment": "больничный продлён" }
```

Ограничения: продлевается только живое замещение (`409` иначе); новая дата позже
начала периода, позже текущего окончания и не в прошлом (`400`); пересечение с другим
активным замещением того же сотрудника — `409`.

Флаг `mandatory_read: true` превращает инструкцию в лист ознакомления: сотрудникам
из круга читателей рассылаются уведомления, появляется строка «Не прочитано», учитываемая
в бейдже и дашборде; способы подписи те же, что у приказов (`NONE/CLICK/TOTP/CODE_WORD`).

**Несколько документов у одной инструкции (v1.12).** Ответы `/help*` содержат массив
`files[]` (`id`, `original_name`, `mime_type`, `size_bytes`, `caption`, `pdf_status`,
`pdf_note`, `pdf_ready`, `uploaded_by`). Прежние одиночные поля `file_name` /
`file_mime` / `file_size` оставлены как наследство и описывают первое вложение;
новый код читает `files`. Одиночные файлы, загруженные до 1.12, перенесены в
`help_article_files` миграцией (шаг `m027` / ревизия `0020`) — ничего вручную
перекладывать не нужно. Типы файлов шире, чем у документов приказов:
`allowed_task_file_mimes` (офисные форматы, изображения, текст, архивы) — к инструкции
можно приложить фото схемы подключения или текстовую памятку.

### Видимость статьи (`visibility`)

Не каждая инструкция адресована всем: регламенты согласования, работа с персональными
данными, заметки учредителя. Поле `visibility` задаёт круг читателей:

| Значение | Кто видит | Кто может задать |
|---|---|---|
| `ALL` | все авторизованные сотрудники (поведение по умолчанию) | Администрация и Владелец |
| `ADMIN` | только администрация (`ADMIN` и `OWNER`) | Администрация и Владелец |
| `OWNER` | только Владелец | только Владелец |

Правила, которые стоит знать при интеграции:

* статья недоступной видимости для роли **не существует**: её нет в `GET /help`,
  в `GET /help/categories`, в глобальном `GET /search`, а прямой запрос
  `GET /help/{id}` (как и скачивание файла, и отметка «Ознакомлен») возвращает **404**,
  а не 403 — сам факт наличия служебной инструкции не раскрывается;
* администрация не может задать `OWNER`: такую статью её же автор не смог бы
  ни прочитать, ни исправить (`403`);
* лист ознакомления ограничивается тем же кругом: у учителя не появляется «долг»
  по инструкции для администрации. Смена `visibility` у обязательной инструкции
  пересчитывает лист (лишние отметки удаляются, новым читателям добавляются),
  действие пишется в журнал как `HELP_SHEET_RESCOPE`;
* `GET /help/mine/pending` учитывает видимость, поэтому бейдж «не прочитано»
  не может прийти от невидимой статьи.

```bash
# служебная инструкция только для администрации, обязательная к прочтению
curl -X POST "$API/help" -H "Authorization: Bearer $ADMIN" -H 'Content-Type: application/json' \
  -d '{"title":"Регламент согласования приказов","category":"Служебное",
       "mandatory_read":true,"visibility":"ADMIN"}'

# у учителя её нет ни в списке, ни по прямому id
curl -s "$API/help" -H "Authorization: Bearer $TEACHER"          # статьи нет
curl -s -o /dev/null -w '%{http_code}\n' "$API/help/$ID" -H "Authorization: Bearer $TEACHER"  # 404
```

### Параметры `GET /helpdesk`

`status`, `category`, `priority`, `mine` (у меня в работе), `unassigned` (без
исполнителя), `overdue` (норматив реакции истёк), `author_id`, `q` (поиск по теме,
описанию, кабинету), `year`, `limit` (по умолчанию 100).

### Жизненный цикл

```
NEW ──take──► IN_PROGRESS ──resolve──► RESOLVED ──confirm──► CLOSED
 │                 ▲                        │
 │                 └───────reopen───────────┘   (автор: «не решено»)
 ├─reject─► REJECTED     (сисадмин, с обязательной причиной)
 └─cancel─► CANCELLED    (автор отозвал)
```

Переходы описаны таблицей `app/enums.py::TICKET_TRANSITIONS` и проверяются на
сервере: невозможный переход — `409`, а не «тихая» порча данных. `RESOLVED`
закрывает **автор**, а не исполнитель: «починили» должно означать «у учителя
действительно работает». Если автор молчит `TICKET_AUTOCLOSE_DAYS` (5) дней,
ночная задача `housekeeping` закрывает заявку сама и ставит `auto_closed=true`.

### Норматив реакции (SLA)

`TICKET_SLA_HOURS`: `URGENT` — 2 ч, `HIGH` — 4 ч, `NORMAL` — 8 ч, `LOW` — 24 ч.
Это норматив **реакции** (взятия в работу), а не срок починки: починка зависит от
запчастей, а отреагировать администратор обязан. Значение копируется в заявку при
создании (`sla_hours`) и пересчитывается при смене приоритета, поэтому изменение
справочника не переписывает историю. Сервер вычисляет `sla_deadline`,
`sla_breached` и фактические `reaction_minutes`; просрочка подсвечивает строку
журнала, доступна фильтром `overdue=true` и шлёт уведомление `TICKET_SLA_BREACH`
всем системным администраторам — один раз на заявку (`sla_notified_at`).

### Вложения и PDF-копия

У каждого файла заявки — `pdf_status` / `pdf_note` / `pdf_ready` (см. §6).
Фото поломки приходит как есть (`NA` для JPEG/PNG не мешает открытию: браузер
показывает изображение сам), а Word/Excel/PowerPoint получают PDF-копию и
открываются в новой вкладке. Вложение помечено `kind`: `AUTHOR` — приложил автор,
`STAFF` — системный администратор (акт, счёт).

### Уведомления и аудит

О новой заявке узнают **все** системные администраторы (очередь общая — иначе
обращение к одному человеку потерялось бы в отпуске); о смене статуса — автор.
Действия пишутся в журнал: `TICKET_CREATE`, `TICKET_UPDATE`, `TICKET_TAKE`,
`TICKET_RESOLVE`, `TICKET_CLOSE`, `TICKET_REOPEN`, `TICKET_REJECT`,
`TICKET_CANCEL`, `TICKET_DELETE`, `TICKET_MESSAGE`, `TICKET_MESSAGE_DELETE`,
`TICKET_FILE`, `TICKET_FILE_DELETE`, `TICKET_SLA_BREACH`.

Типичный цикл:

```bash
# учитель сообщает о поломке
T=$(curl -s -X POST $API/helpdesk -H "$TEACHER_AUTH" -H 'Content-Type: application/json' -d '{
  "title":"Зажевало бумагу в принтере","description":"Печатает второй лист и мнёт",
  "category":"PRINTER","priority":"HIGH","location":"кабинет 214","contact_phone":"2-14"}' \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["id"])')
curl -s -X POST $API/helpdesk/$T/files -H "$TEACHER_AUTH" -F "file=@photo.jpg;type=image/jpeg" > /dev/null

# системный администратор берёт в работу, чинит, отправляет автору на подтверждение
curl -s -X POST $API/helpdesk/$T/take    -H "$SYSADMIN_AUTH" -d '{}'
curl -s -X POST $API/helpdesk/$T/resolve -H "$SYSADMIN_AUTH" \
     -d '{"resolution":"Заменил картридж, прочистил ролики подачи"}'

# автор подтверждает — заявка закрыта
curl -s -X POST $API/helpdesk/$T/confirm -H "$TEACHER_AUTH" -d '{"comment":"работает, спасибо"}'
```

### Одноразовые билеты: выгрузка данных и WebSocket

Браузер не может приложить заголовок `Authorization` ни к WebSocket-подключению,
ни к GET, скачивающему файл. Прежние обходы были небезопасны: дамп БД и архив всех
документов школы отдавались по обычному access-токену без подписи, а WebSocket
принимал access-токен в query-строке, которая попадает в access-логи nginx и DSM.

Схема теперь двухшаговая:

```bash
# 1) подпись операции «код из аутентификатора + контрольное слово» → билет
TICKET=$(curl -s -X POST "$API/system/export-ticket" -H "Authorization: Bearer $OWNER" \
  -H 'Content-Type: application/json' \
  -d '{"target":"db_backup","pep_code":"481902","pep_word":"голубой-кит"}' | jq -r .ticket)

# 2) скачивание по билету (он одноразовый: повторное предъявление → 403 TICKET_INVALID)
curl -o backup.sql "$API/system/backup?ticket=$TICKET" -H "Authorization: Bearer $OWNER"
```

| Параметр | Значение |
|---|---|
| `target` | `db_backup` (дамп БД) или `files_zip` (архив файлов) |
| срок жизни | 120 с на выгрузку, `WS_TICKET_TTL_SEC` (60 с) на WebSocket |
| однократность | билет удаляется при первом предъявлении |
| привязка | к цели (`purpose`) и к пользователю: чужой билет и билет «от другой операции» отклоняются |

Коды ошибок: `TICKET_MISSING` (билет не передан), `TICKET_INVALID` (не существует,
уже использован, чужой или не для этой операции), `TICKET_EXPIRED` (истёк — подпишите
заново). Билеты хранятся в памяти процесса, поэтому backend работает с `--workers 1`.

Типы уведомлений: `ORDER_PUBLISHED`, `ORDER_UPDATED`, `ORDER_ACK_DEADLINE`,
`TASK_ASSIGNED`, `TASK_STATUS_CHANGED`, `TASK_MARK`, `TASK_COMMENT`,
`PLAN_PUBLISHED`, `PLAN_UPDATED`, `HOUSEKEEPING` (автоочистка БД), `FILES_RESTORE`
(восстановление файлов школы), `NOTE_ON_APPROVAL`, `NOTE_APPROVED`, `NOTE_REJECTED`,
`NOTE_COMPLETED` (служебные записки), `SUBSTITUTION_ASSIGNED`, `SUBSTITUTION_INFO`,
`SUBSTITUTION_TASKS`, `SUBSTITUTION_CONFIRMED`, `SUBSTITUTION_CANCELLED` (замещения),
`HELP_MANDATORY` (обязательная инструкция). `entity_type` уведомления:
`order` | `task` | `plan` | `service_note` | `substitution` | `help_article`.

Действия журнала: `LOGIN`, `LOGIN_FAILED`, `LOGOUT`, `PASSWORD_CHANGE`, `ORDER_CREATE`,
`ORDER_UPDATE`, `ORDER_PUBLISH`, `ORDER_ARCHIVE`, `ORDER_DELETE`, `ORDER_FILE_UPLOAD`,
`ORDER_FILE_DELETE`, `ORDER_ACK`, `ORDER_RECIPIENTS`, `TASK_CREATE`, `TASK_UPDATE`,

## 11. Формат ошибок

```json
{ "detail": "Недостаточно прав", "code": "FORBIDDEN" }
```

| HTTP | Когда |
|---|---|
| `400` | Неверные данные или файл (MIME, размер, пустой файл, `date_from > date_to`) |
| `401` | Нет/истёк/неверный токен; неверный пароль (локальный или доменный) |
| `403` | Недостаточно прав (роль или точечное правило доступа) |
| `404` | Сущность не найдена |
| `409` | Конфликт: дубликат номера приказа, повторное ознакомление, недопустимый переход статуса, защита единственного Владельца |
| `422` | Ошибка валидации схемы (сообщения собираются в одну строку) |
| `429` | Превышен лимит неудачных попыток входа (защита доменных учёток от блокировки) |
| `503` | Контроллер домена недоступен (`code: AD_ERROR`) |
| `500` | Внутренняя ошибка (детали — только в логах сервера) |

## 12. Пример сквозного сценария (bash)

```bash
API=http://localhost:8000/api/v1

# 1) вход администрации
TOKEN=$(curl -s -X POST $API/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"admin@schoolhub.ru","password":"Demo1234!"}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["access_token"])')
AUTH="Authorization: Bearer $TOKEN"

# 2) черновик приказа
ORDER=$(curl -s -X POST $API/orders -H "$AUTH" -H 'Content-Type: application/json' -d '{
  "number":"900-к","order_year":2026,"title":"О проведении педсовета",
  "order_type":"EDUCATION","issued_on":"2026-10-12","ack_deadline":"2026-10-20"}' \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["id"])')

# 3) загрузка PDF и публикация
curl -s -X POST $API/orders/$ORDER/files -H "$AUTH" -F "file=@prikaz.pdf;type=application/pdf" > /dev/null
curl -s -X POST $API/orders/$ORDER/publish -H "$AUTH" | python3 -m json.tool | head -8

# 4) учитель подтверждает ознакомление
TT=$(curl -s -X POST $API/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"ivanov@schoolhub.ru","password":"Demo1234!"}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["access_token"])')
curl -s -X POST $API/orders/$ORDER/acknowledgements -H "Authorization: Bearer $TT" \
  -H 'Content-Type: application/json' -d '{"comment":"Ознакомлен"}' | python3 -m json.tool

# 5) лист ознакомления глазами администрации
curl -s "$API/orders/$ORDER/ack-summary" -H "$AUTH" | python3 -m json.tool
```

## 13. Версии и совместимость

* Версия API зашита в префикс `/api/v1`; breaking-изменения — только в новом префиксе.
* OpenAPI-схема генерируется из кода (`app.openapi()`), поэтому документация не расходится с реализацией.
* Клиентский контракт продублирован в `frontend/src/types.ts`; при изменении схем его нужно синхронизировать
  (в перспективе — генерация `openapi-typescript`).
* **PDF-копия документа (v1.12)** — сквозное поведение четырёх разделов (служебные
  записки, задачи, инструкции, заявки техподдержки): у каждого файла `pdf_path`,
  `pdf_size`, `pdf_status` (`NA`/`PENDING`/`READY`/`FAILED`) и `pdf_note`.
  `?inline=true` отдаёт копию, когда она готова, и оригинал — когда нет; обычное
  скачивание всегда отдаёт оригинал. Оригинал не заменяется и не удаляется.
* Устаревшие, но работающие маршруты: `POST /help/{id}/file` и
  `GET /help/{id}/file/download` (заменены на `/files`), поля `file_name` /
  `file_mime` / `file_size` в ответах `/help*` (заменены массивом `files[]`).
