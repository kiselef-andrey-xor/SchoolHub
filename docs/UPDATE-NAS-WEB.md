# Обновление SchoolHub на Synology NAS (веб-интерфейс и SSH)

> **Пошаговый сценарий для администратора школы — [`ОБНОВЛЕНИЕ.txt`](../ОБНОВЛЕНИЕ.txt)**
> в корне репозитория (он же кладётся в архив обновления). Этот документ — справочная
> часть: что именно происходит при обновлении, чем отличаются версии, как проверять
> результат и как откатываться. Редакция — **1.12.0**.

Обновление подходит для DSM 7.x с **Container Manager** и для установки, развёрнутой
по [`УСТАНОВКА.txt`](../УСТАНОВКА.txt) / `docs/INSTALL.md`. Все данные школы
(база, вложения, ключ сессий) живут в именованных томах `db_v2 / uploads_v2 / secrets_v2`
и при обновлении **не перезаписываются**: заменяются только исходный код и образы
контейнеров.

## 0. Правило №1 — сначала копия

Обновление накатывает на боевую базу новые шаги схемы. Шаги идемпотентны и только
добавляют таблицы/колонки, но отменять их назад система не умеет. Поэтому до любых
изменений делается и **проверяется** резервная копия:

| Что | Зачем | Чем |
|---|---|---|
| Дамп БД | единственная часть, которую меняет обновление | кнопка «Скачать резервную копию БД» (Профиль Владельца) или `pg_dump` через SSH |
| Архив вложений | документы приказов, вложения задач, сканы, аватары | `tar` тома `uploads_v2` (SSH или временный контейнер) |
| Конфигурация | откат на прежний compose/.env | копия `docker-compose.yml`, `.env` |
| Ключ сессий | чтобы не выгонять всех при откате | копия `secrets_v2/secret_key` (только SSH) |
| Старый код | быстрый откат версии | переименование `backend` → `backend.old-<дата>` |

Копии складываются в новую папку на NAS (`/volume1/backup/schoolhub/update-<дата>/`)
и дублируются **вне** машины (USB-диск, Hyper Backup, рабочий компьютер). Проверка —
размер, контрольная сумма, `tar -t`, `grep -c "CREATE TABLE"` в дампе; при наличии
времени — накат дампа во временный контейнер PostgreSQL (сценарий в `ОБНОВЛЕНИЕ.txt`).

| 1.10.0 → **1.11.0** | служебные записки: каждый видит только своё (автор/исполнитель/согласующий), Владелец — всё и может выдать грант «Все служебные записки»; удаление записок Владельцем (в т.ч. утверждённых); кнопка «Печать» больше не отдаёт 401; видно, КТО согласовал. Замещения: задачи/планы/ВШК передаются только после подтверждения замещающим и возвращаются отсутствующему при отмене, завершении и удалении строки; появилось продление периода; строки удаляют Владелец и кадровик (грант «Кадровик: замещения»); поправлена вёрстка кнопок. Селектор «Подпись ознакомления» в форме приказа; файлы инструкций открываются во всплывающем окне; ровная сетка карточек справки; QR-код при привязке аутентификатора; приветствие — только имя и случайная форма; выход на экран входа после 3 часов неактивности; из левого меню убраны дубликаты («Уведомления», карточка профиля) | миграции применяются автоматически (`0016`–`0018` / шаги `m023_notes_full_access`, `m024_substitution_transfer`, `m025_substitutions_access`); после обновления решить, кому нужны гранты «Все служебные записки» и «Кадровик: замещения» (Пользователи → карточка → «Права доступа») — по умолчанию оба выключены; сотрудники увидят свои замещения, но не чужие |

Полный перечень — [`docs/CHANGELOG.md`](CHANGELOG.md).

**Схема базы.** Миграции применяются автоматически при старте контейнера
(`AUTO_MIGRATE=true`): сначала `alembic upgrade head`, затем идемпотентные шаги
`backend/app/migrations.py` (`m001`…`m027`). Установка «по ВШК» стоит на шаге
`m014_certifications`; при старте 1.12.0 доедут `m015_equipment_barcode`,
`m016_user_birth_date`, `m017_user_list_views`, `m018_system_flags`,
`m019_totp_pep`, `m020_journal_modules`, `m021_help_visibility`,
`m022_task_occurrences`, `m023_notes_full_access`, `m024_substitution_transfer`,
`m025_substitutions_access`, `m026_helpdesk`, `m027_document_pdf`. В журнале
`schoolhub-backend` это строки вида `migrations: users.totp_enabled добавлена`,
`migrations: таблица service_notes создана`. Они появляются один раз — при первом
старте после обновления.

## 2. Ход обновления (кратко)

Подробные команды и скриншотные пути — в `ОБНОВЛЕНИЕ.txt`. Порядок всегда один:

1. **Записать исходное состояние**: адрес, путь к проекту (`APP_ROOT`), версию
   (`GET /api/v1/health` → `"version"`), дату начала.
2. **Сделать и проверить копию** (раздел 0).
3. **Остановить проект**: Container Manager → Проект → `schoolhub` → «Остановить».
4. **Заменить код**: старые `backend/` и `frontend/` переименованы в `*.old-<дата>`,
   архив обновления извлечён в папку проекта.
5. **Проверить `docker-compose.yml` и `.env`** (см. раздел 3).
6. **Пересобрать**: Container Manager → «Пересобрать» (SSH:
   `docker compose build --no-cache && docker compose up -d`).
   На DS223/arm64 — 10–20 минут.
7. **Проверить**: `/api/v1/health` → `"version": "1.12.0"`; журнал backend —
   `Application startup complete`, ошибок нет; вход под Владельцем и учителем;
   прежние данные на месте (приказы, задачи, планы, ВШК, инвентарь, движение,
   входящие, аттестация); вложения открываются; новые разделы видны;
   Профиль → «Файлы школы» — сводка без «битых ссылок». Полный список проверок
   версии — ШАГ 6 в `ОБНОВЛЕНИЕ.txt` (пункты 16–20 про техподдержку, PDF-копию,
   печатный бланк записки и резервный доступ).
8. **После обновления**: привязать аутентификатор Владельца (ПЭП) и проверить, что
   контрольное слово задано, назначить системных администраторов техподдержки,
   сменить пароль Владельца (если он был из старой редакции compose), настроить
   `backup-db.sh` в планировщике DSM, через неделю удалить `*.old-<дата>`.

## 3. `docker-compose.yml` и `.env` при переходе на 1.8.0+

Редакция compose от 13.10.2026 (машина «по ВШК») содержала захардкоженные
`SECRET_KEY` и учётные данные Владельца; репозиторий публичный, значит оба значения
скомпрометированы. Редакция от 28.10.2026 и новее секретов не содержит:

* `SECRET_KEY` пуст — ключ берётся из `SECRET_KEY_FILE=/data/secrets/secret_key`
  (том `secrets_v2`, права 0600) и генерируется при первом старте
  (`app/config.py::_resolve_secret_key`);
* первый Владелец создаётся через веб-страницу по одноразовому коду из журнала
  (либо через `OWNER_EMAIL`/`OWNER_PASSWORD`/`OWNER_NAME`/`SCHOOL_NAME` в `.env`);
* пути сборки параметризованы переменной `APP_ROOT`.

Поэтому compose-файл **заменяется**, а в новый переносятся только ваши значения:
`APP_ROOT`, `HTTP_PORT`, `POSTGRES_PASSWORD`, `TZ`, `LDAP_*`. Имена томов
(`db_v2`, `uploads_v2`, `secrets_v2`) менять нельзя — иначе данные «исчезнут»
из поля зрения контейнеров (на диске они останутся).

Новые необязательные переменные (значения по умолчанию безопасны):

```dotenv
APP_ENV=prod                    # отключает /docs и /openapi.json на боевой машине
CORS_ORIGINS=[]                 # «*» игнорируется: с allow_credentials это дыра
TOTP_MAX_ATTEMPTS=5             # троттлинг подбора кода/слова электронной подписи
TOTP_LOCK_WINDOW_MIN=15
FILES_ARCHIVE_MAX_MB=512
FILES_ARCHIVE_UNPACKED_MAX_MB=4096
DOC_CONVERT_TIMEOUT_SEC=60
```

Образец — [`.env.example`](../.env.example).

### Про `SECRET_KEY`, сессии и привязки ПЭП

* Ключ изменился → все сессии сброшены, пользователи входят заново. Это ожидаемо.
* Сохранить прежний ключ можно: положите его в том `secrets_v2` файлом `secret_key`
  (права 0600). Но ключ из старой редакции compose считается скомпрометированным —
  рекомендуемый путь позволить системе сгенерировать новый.
* **Важно для установок 1.7.0/1.8.0**: секрет аутентификатора (ПЭП) шифруется
  ключом, производным от `SECRET_KEY`. Ротация ключа делает существующие привязки
  нечитаемыми — их придётся сбросить (Владелец: карточка сотрудника →
  «🔑 Сбросить аутентификатор») и привязать заново. На машине «по ВШК» привязок
  ещё нет, поэтому ротация ничем не грозит.

## 4. Откат

| Ситуация | Действия |
|---|---|
| Новая сборка не стартует/ведёт себя неверно, данные целы | Остановить проект → вернуть имена `backend.old-*`/`frontend.old-*` → вернуть прежний `docker-compose.yml` → «Пересобрать» → «Запустить». Применённые шаги миграций остаются: они только добавляли таблицы/колонки истарой версии не мешают |
| База повреждена | Остановить проект → вернуть старый код → восстановить дамп (`deploy/synology/restore-db.sh <файл>` по SSH или Профиль → «Резервное копирование» → «Восстановить из копии») → при необходимости вернуть файлы из `uploads-*.tar.gz` → пересобрать и проверить |
| Не поднимается `schoolhub-db` | Проверить свободное место на томе и журнал контейнера; дамп восстанавливать в новый том, не удаляя старый |

`restore-db.sh` перед накатом сам делает копию текущей базы (`<дамп>.pre-restore`)
и сбрасывает схему `public` — восстановление полное, не «доливка».

## 5. Проверка копии на временном контейнере

```bash
docker run -d --name sh-verify -e POSTGRES_PASSWORD=test -e POSTGRES_DB=schoolhub \
    -e POSTGRES_USER=schoolhub -p 127.0.0.1:55432:5432 postgres:16-alpine
sleep 15
gunzip -c /volume1/backup/schoolhub/update-<дата>/db-before-update.sql.gz \
    | docker exec -i sh-verify psql -U schoolhub -d schoolhub -q
docker exec -i sh-verify psql -U schoolhub -d schoolhub \
    -c "select count(*) from users; select count(*) from orders;"
docker rm -f sh-verify
```

Порт опубликован только на `127.0.0.1`: временная база с персональными данными
не должна быть видна в сети школы.

## 6. Частые проблемы

| Симптом | Причина / что делать |
|---|---|
| Сайт не открывается после пересборки | Все три контейнера должны быть «Выполняется» и «Исправно»; смотреть журнал `schoolhub-backend`. Чаще всего — ошибка в перенесённых значениях `APP_ROOT`/`HTTP_PORT` |
| `relation … does not exist`, `column … does not exist` | Миграции не применились: проверить `AUTO_MIGRATE=true`, перезапустить проект. Не помогло — откат и журнал в поддержку |
| Все «вылетели», просят войти | Сменился `SECRET_KEY` (раздел 3). Пароли не менялись |
| Кнопка «Скачать резервную копию БД» просит код и слово | Так работает 1.8.0+: выгрузка всех персональных данных — только по подписи ПЭП. Привяжите аутентификатор (Профиль → «Электронная подпись») |
| «🗑 Удалить» сотрудника открывает окно подписи | Удаление учётки — операция «код + слово». До 1.9.0 кнопка отправляла запрос без подписи и получала 409 |
| Импорт инвентаря отклоняет строки про штрихкод | С 1.9.0 в поле нельзя хранить кавычки, `< >`, `&`, обратную косую и управляющие символы (защита от внедрения кода в SVG этикетки), длина — не больше 128. Цифры, латиница, кириллица и обычные разделители проходят |
| В Excel ячейки выгрузок начинаются с `'` | Защита от формульных инъекций (CWE-1236): апостроф не печатается, но не даёт исполнить значение как формулу |
| Пересборка падает на `npm ci`/vite | На DS223 не хватает памяти: остановить другие контейнеры и индексацию, повторить сборку |
| Пропали вложения приказов | Файлы в томе `uploads_v2`, обновление его не трогает. Проверить монтирование тома и `UPLOAD_DIR`; Профиль → «Файлы школы» покажет число файлов на диске |
| Уведомления не мгновенные | В `deploy/synology/dsm-reverse-proxy.conf` нужны заголовки `Upgrade`/`Connection`; без них система работает на поллинге раз в 45 секунд |

## 7. После обновления

1. **Привязать аутентификатор Владельца** и задать контрольное слово (записать на
   бумаге). Без этого недоступны: выгрузка дампа и архива файлов, восстановление
   из копии, локдаун, удаление учётных записей.
2. **Сменить пароль Владельца**, если использовалась учётка изстарой редакции compose.
3. **Наладить ежедневные копии**: `deploy/synology/backup-db.sh` + задача
   планировщика DSM (root, 03:30); папку с дампами включить в Hyper Backup.
4. **Сообщить сотрудникам**: войти заново; появились разделы «Служебные записки»,
   «Замещения», «Справка», «Уведомления»; ознакомление с приказами о движении
   обучающихся подписывается кодом из приложения — учителям тоже стоит привязать
   аутентификатор. Инструкции — в `instructions/`.
5. Через неделю штатной работы удалить `backend.old-*` / `frontend.old-*`;
   папку копии хранить до следующего обновления.
