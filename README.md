# SchoolHub — веб-приложение для школы

Единая цифровая среда школы: **электронные приказы с подтверждением ознакомления**, **Task Manager
с несколькими исполнителями**, **планы работы на неделю**, **служебные записки с печатным бланком**
и **техподдержка школы** — с ролевой моделью доступа (RBAC).

| Слой | Стек |
|---|---|
| Backend | Python 3.12, FastAPI, SQLAlchemy 2 (async), Pydantic v2, PostgreSQL 16 (asyncpg), JWT |
| Frontend | React 18 + TypeScript, Vite, TanStack Query, React Router, CSS-токены (без UI-библиотек) |
| Аутентификация | Локальные учётки (bcrypt) **или Active Directory** — LDAP/LDAPS bind, авто-провижининг, группы AD |
| Инфраструктура | Docker Compose, nginx (reverse-proxy + статика), локальное файловое хранилище (заменяемо на S3/MinIO) |
| Развёртывание | x86-сервер **или Synology NAS (arm64)** — готовый комплект в `deploy/synology/` |
| Качество | интеграционные тесты (pytest + httpx/ASGI), сквозной smoke-тест сценариев, CI: линтеры, сверка схемы БД с моделями, типы и сборка фронтенда (`make check`) |

## 0. Установка на Synology NAS — 5 шагов

🚀 **Пошаговая инструкция: [`docs/INSTALL.md`](docs/INSTALL.md)** — обязательных настроек нет:
`SECRET_KEY` генерируется автоматически, первого Владельца вы создадите в браузере.

**SSH не нужен**: скопируйте проект в `/docker` через File Station и создайте проект
в **Container Manager → Проект → Создать** (файл `deploy/synology/docker-compose.yml`).

sudo bash install-nas.sh

Скрипт соберёт образы, запустит стек и напечатает **код первоначальной настройки**.
Дальше: `http://<адрес-NAS>:8080` → ввести код → создать Владельца → добавить сотрудников.

## 2. Функциональные возможности

### 2.1 Аутентификация и RBAC

* Локальные учётные записи (bcrypt) — основной режим; **опционально** Active Directory
  (LDAP/LDAPS bind, авто-провижининг, импорт из каталога) — см. [`docs/AD-OPTIONAL.md`](docs/AD-OPTIONAL.md).
* **Удаление пользователей** (только Владелец): учётка скрывается из всех списков и не может
  войти, e-mail/логин освобождаются, но история (приказы, ознакомления, задачи) сохраняется;
  удалённые видны Владельцу через «показывать удалённые» и восстанавливаются кнопкой.
* **Требовать смену пароля** (флаг ставит только Владелец в карточке сотрудника; автоматически
  ставится при сбросе пароля администратором): до смены пароля интерфейс показывает
  неотклоняемое окно смены. «Последний вход» обновляется и живой сессией (порог 5 минут).
* **Резервное копирование**: кнопка «Скачать резервную копию БД» в профиле Владельца
  (`GET /system/backup`, pg_dump plain SQL) + ежедневные дампы с ротацией `backup-db.sh`
  и восстановление `restore-db.sh` (deploy/synology, планировщик DSM).
* **Восстановление из копии** (только Владелец): кнопка рядом с резервной копией в профиле —
  загрузите .sql-дамп, введите подтверждающее слово, и база полностью заменится
  (`POST /system/restore`). Дамп применяется одной транзакцией: при ошибке старые данные
  сохраняются. После восстановления все пользователи входят заново.
* Локальная учётка **не требует e-mail**: при создании без e-mail (вручную или массовой
  загрузкой таблицей «ФИО, ПАРОЛЬ[, e-mail[, роль]]») вход идёт по сгенерированному логину —
  транслитерация ФИО (`Иванова Иванна` → `ivanova.ivanna`, при коллизии — суффикс).
  Массовая загрузка: раздел «Пользователи» → «⬆ Массовая загрузка» (вставка из буфера или
  CSV/TSV-файл, предпросмотр с построчными ошибками, шаблон таблицы).
* Самообслуживание: смена собственного пароля в профиле (локальные учётки; все сессии после
  смены отзываются) и загрузка аватара (JPEG/PNG/WebP до 5 МБ, `POST /users/me/avatar`,
  отображается в списках, шапке и профиле).
* Мастер первоначальной настройки: первый Владелец создаётся в браузере по одноразовому
  коду из журнала контейнера (или одной командой `scripts/first_owner.py`), `SECRET_KEY`
  генерируется автоматически — установка не требует ручных секретов.
* До завершения настройки весь API закрыт (`503 SETUP_REQUIRED`), кроме `/health` и `/setup/*`.
* JWT access (30 мин, только в памяти вкладки) + refresh (14 дней) в **httpOnly-cookie**
  (`SameSite=strict`, путь `/api/v1/auth`) — XSS не может ни прочитать, ни отправить его на чужой сайт.
* **Refresh-сессии отзываемы**: каждый токен хранится в БД (`refresh_sessions`) и **ротируется**
  при каждом обмене; выход, смена/сброс пароля и блокировка учётки отзывают сессии немедленно;
  повторное предъявление заменённого токена (вне 30-секундного окна для параллельных вкладок)
  трактуется как кража — семейство сессий отзывается целиком, событие пишется в аудит.
* **Выход по неактивности** (v1.11): 3 часа без мыши/клавиатуры/прокрутки — и приложение
  возвращает на экран входа (метка активности общая для всех вкладок, хранится в `localStorage`,
  проверяется в том числе сразу при открытии страницы). Лимит — `VITE_IDLE_LIMIT_MIN` при сборке
  фронтенда (по умолчанию 180 минут); серверные сроки токенов при этом не меняются.
* 3 роли: `OWNER` (Владелец), `ADMIN` (Администрация), `TEACHER` (Учитель) — иерархия `TEACHER(1) < ADMIN(2) < OWNER(3)`.
* Права проверяются **двумя независимыми слоями**:
  1. **API**: зависимости `require_role(...)` выполняются до хендлера + точечные проверки в сервисах
     (например, учитель не может переназначить задачу или изменить дедлайн).
  2. **UI**: набор `capabilities` приходит с сервера в `GET /auth/me`, по нему скрываются разделы и кнопки.
     Фронтенд **не является** границей безопасности — при подмене клиента API вернёт 403.
* Защита от эскалации: нельзя выдать роль своего уровня или выше (кроме Владельца), нельзя разжаловать
  или заблокировать самого себя, в школе всегда остаётся хотя бы один активный Владелец.
* Сквозной журнал событий (`audit_log`): кто, что, когда, с какого IP и какие поля изменились (diff).
  Владелец может **очистить журнал** (`DELETE /audit`, кнопка в разделе «Журнал»); факт очистки
  сам остаётся первой записью нового журнала.
* Логин учётки без e-mail генерируется из ФИО автоматически; задать логин вручную при создании
  и **менять его может только Владелец** (поле в форме редактирования пользователя).

### 2.2 Модуль «Приказы»

* Просмотр документов **PDF** (инлайн-превью в браузере) и **DOCX**: при загрузке Word-файла
  сервер фоном конвертирует его в PDF (LibreOffice headless входит в образ), поэтому документ
  открывается прямо в браузере, а оригинал .docx всегда доступен для скачивания.
* Жизненный цикл: `Черновик → Опубликован → Архив` (переходы валидируются, архив read-only).
  **Опубликованный приказ неизменяем**: редактирование и замена/загрузка документа отклоняются
  (409) — доступны только просмотр, ознакомление, круг ознакомления и перевод в архив.
  Черновик удаляет ADMIN/OWNER; **архивный приказ безвозвратно удаляет только Владелец**
  (вместе с документом и листом ознакомления, в журнале остаётся запись об удалении).
* Версионирование файлов: каждая загрузка в черновике — новая версия, история и sha256-контроль
  суммы сохраняются; после публикации документ замораживается.
* Фильтрация: полнотекстовый поиск, тип приказа, статус, период по дате, «есть неподписанные»,
  «ждут моей подписи»; пагинация; синхронизация фильтров с URL.
* Статус **«Ознакомлен»**: явное подтверждение с фиксацией времени, IP и User-Agent (аналог подписи
  в бумажном листе ознакомления), повторное подтверждение невозможно (409).
* Лист ознакомления: круг подписчиков — **все сотрудники или выбранный список** (задаётся ещё
  в черновике, меняется и после публикации — подписи ознакомившихся сохраняются), прогресс,
  **печатная форма** (кнопка «Печать»: реквизиты приказа — номер, год, тип, даты, срок, автор,
  прогресс — и таблица ознакомившихся с колонкой подписи), экспорт CSV;
  список неподписавших, экспорт в CSV для отчётности.
* Валидация загрузки: только PDF/DOCX/DOC, до 25 МБ, отказ на пустой файл и чужой MIME-тип;
  **содержимое сверяется с сигнатурой формата** (`%PDF-`, OOXML-пакет, OLE2) — подделанный
  `Content-Type` не спасает; защита от path traversal (`is_relative_to`, content-addressed пути).

### 2.3 Task Manager

* Создание задач, **несколько исполнителей**, дедлайн, приоритет (`LOW/NORMAL/HIGH/URGENT`).
* У каждого исполнителя — **своя отметка «выполнено»**: первая отметка переводит задачу
  в «В работе», когда отметки поставили все — задача автоматически закрывается;
  снятие отметки возвращает задачу в работу.
* **Вложения задач**: офисные файлы, изображения, архивы (до 25 МБ, sha256),
  скачивание участниками, удаление — загрузившим/постановщиком/администрацией.
* Статусы: **Новая → В работе → Выполнена**, плюс **Просрочена**.
* **«Просрочена» — вычисляемое состояние**, а не значение в БД: `status != DONE AND deadline < now`.
  Оно наступает само по себе, поэтому хранить его нельзя (данные устаревали бы без cron'а).
  Сервер считает его в SQL-предикатах и отдаёт полями `effective_status` / `is_overdue` / `days_left`.
* Видимость: учитель — только свои задачи (и 403 на чужие), админ/владелец — все.
* Учитель может менять статус и описание своей задачи, но **не** исполнителей, дедлайн и приоритет.
* State machine переходов статусов, история изменений, комментарии (только для участников задачи),
  уведомления исполнителям и постановщику (назначение, отметки, закрытие).
* Отчёт по просрочкам в разрезе исполнителей (`GET /tasks/overdue-report`).
* **Повторяющиеся задачи** (`recurrence = DAILY/WEEKLY/MONTHLY`): одна строка в БД — копии
  на каждый период НЕ плодятся. Выполненная в текущем периоде задача автоматически возвращается
  в «Новую» к началу следующего (каждый день / выбранные дни недели / число месяца; 29–31
  переносится на последний день короткого месяца). Автосброс (`services/tasks.py::rollover_due`)
  выполняется из фонового цикла напоминаний и страховочно — при чтении списков/карточек задач;
  записи в историю и аудит при сбросе не пишутся осознанно (иначе ежедневная задача давала бы
  сотни одинаковых строк шума). Дедлайна и состояния «Просрочена» у повторяющихся задач нет:
  срок задаёт сам период. `last_done_at` хранит, когда задачу выполняли в последний раз,
  API отдаёт `done_this_period`, список фильтруется параметром `recurring`.

### 2.4 История действий по задачам и «Движение обучающихся»

* **История задачи** пишет все действия, а не только статусы: назначение и снятие
  исполнителей (с именами), правки названия/описания/срока/приоритета/входящего номера,
  добавление и удаление файлов, комментарии — с автором и временем.
* **Раздел «Движение обучающихся»** (доступ выдаёт Владелец галочкой в карточке сотрудника):
  приказы о переводе/зачислении/отчислении по реквизитам бумажного образца (тип, законный
  представитель, обучающийся, дата рождения, откуда/куда, дата и № приказа, подписант);
  печать готового документа с шапкой школы и «ПРИКАЗЫВАЮ…»; статусы новый/выполнен/ошибка;
  сводка по отмеченным чекбоксами приказам — копирование таблицей (TSV) и CSV для внешних систем.
* В журнале событий исполнитель показывается **фамилией с инициалами** (actor_name денормализован
  на момент действия), e-mail — только как дополнение; «система» остаётся для анонимных событий.

### 2.5 Учёт оборудования, данные школы и напоминания

* **«Инвентарь»** — учёт оборудования: наименование, инвентарный номер, заводской (серийный)
  номер, количество, местонахождение, примечание; поиск, CSV-выгрузка; доступ выдаёт Владелец
  галочкой в карточке сотрудника (capability `equipment:read`).
* **Данные школы** правит Владелец: «Профиль → Данные школы» (название попадает в печатные
  формы плана и приказов по движению).
* **Напоминания об ознакомлении** (фоновый цикл в контейнере, `REMINDERS_ENABLED`):
  сотрудникам — in-app уведомление за N дней до дедлайна и в день дедлайна
  (`REMINDER_DAYS_BEFORE`, по умолчанию 3); администрации — ежедневная сводка
  «Просроченные ознакомления» не раньше `REMINDER_HOUR` (9:00) и одноимённый блок
  на дашборде со списком «приказ — сотрудник — срок — дней просрочки».

### 2.6 Журнал входящих писем

* У задачи появляется необязательное поле **«Входящий № письма»**: если оно заполнено,
  в журнале входящих автоматически создаётся запись (№ регистрации по году, дата входящего,
  № входящего, тема и ответственный из задачи); даты отправки, адресат и примечание вносит
  пользователь; изменение/снятие номера синхронизирует/удаляет запись.
* Ручные записи журнала, правка, удаление (Владелец), поиск и фильтр по году.
* Доступ: по умолчанию только Владелец; грант выдаёт Владелец галочкой
  «Доступ к журналу входящих писем» в карточке сотрудника (capability `incoming:read`).
* Экспорт CSV (с BOM для Excel) и печатная форма журнала.
* Точка входа: кнопка «✉ Журнал входящих» на экране задач и маршрут `/incoming`.

### 2.7 Модуль «План работы на неделю»

* Электронный аналог школьного Word-документа «План работы ДД.ММ–ДД.ММ»:
  дежурный класс и классный руководитель, блоки **«В течение месяца»** и **«В течение недели»**,
  таблица мероприятий по дням (пн–сб): мероприятие, время, место, ответственные.
* **Ответственные — ссылки трёх видов**: конкретный сотрудник, **должность целиком**
  (все держатели, напр. «классные руководители») или **«Администрация»** (все с ролью
  OWNER/ADMIN). При публикации все адресаты получают уведомление; на дашборде и в списке
  планов видно «моих пунктов: N». Импорт DOCX распознаёт и сотрудников («Кузнецова О.В.»),
  и должности («зам.директора по УВР», «руководители ШМО»), и «Администрацию».
* Жизненный цикл: **Черновик → Опубликован → Архив** (один план на неделю, дубли запрещены).
* Редактор повторяет структуру документа; неделя пересчитывается автоматически (пн–сб).
* Просмотр — «бумажный» вид как в Word, **печать/PDF** одной кнопкой (печатается только документ).
* Права: создают/редактируют/публикуют — Владелец и Администрация; видят опубликованные
  и архив — все сотрудники.

### 2.8 Должности-роли и модуль «ВШК»

* **Справочник должностей** (`positions`): «Директор», «Заместитель директора по УВР/ВР/НМР/АХР/…»,
  «Классный руководитель», «Руководитель ШМО», «Советник директора по воспитанию», «Главный бухгалтер»
  и т. д. Назначает администрация в карточке сотрудника (несколько должностей на человека);
  свободное текстовое поле «должность» выведено из эксплуатации (старые значения сконвертированы
  миграцией в справочник и назначения). Синонимы должности используются при разборе Word-документов.
* **ВШК (внутришкольный контроль)**: годовой план учебного года (август–июнь) с группировкой
  по направлениям контроля; у мероприятия — цель, вид контроля, ответственные (ссылки, как в плане
  работы), срок и форма подведения итогов, статус («запланировано / проводится / выполнено»),
  результат (текст выводов + файл справки).
* **Импорт DOCX** плана ВШК (таблица «Цель | Вид | Ответственный | Срок и форма» с строками-месяцами
  и строками-направлениями) в черновик года; повторный импорт в черновик заменяет мероприятия,
  в опубликованный план импорт закрыт (правка вручную).
* Жизненный цикл: **Черновик → Опубликован** (уведомление ответственных); черновик виден только
  администрации, опубликованный план — всем; свои мероприятия подсвечены и попадают на дашборд
  в блок «Мой ВШК в этом месяце». Печатная форма годового плана одной кнопкой.
* Глобальный поиск ищет и по мероприятиям ВШК (переход с подсветкой строки).

### 2.9 Глобальный поиск и отчёт «Итоги месяца»

* **Глобальный поиск (Ctrl+K / кнопка 🔍 в шапке)**: приказы, задачи, журнал входящих и
  сотрудники одним запросом; секции выдаются только по правам текущего пользователя
  (учитель не видит чужие задачи и список сотрудников). Клик по результату открывает карточку,
  для журнала/пользователей — страницу с уже подставленным поиском.
* **Отчёт «Итоги месяца»** (кнопка на дашборде, Владелец/Администрация): за выбранный месяц —
  опубликованные приказы с разбивкой по типам и долей полностью ознакомленных, созданные/
  выполненные/просроченные задачи, записи журнала входящих, заявления на движение.
  Печатная форма одной кнопкой.
* Навигация: пункт «Мой профиль» убран из бокового меню — профиль открывается кликом по ФИО
  внизу сайдбара (и через меню под именем в шапке).

### 2.10 Тёмная тема и модуль «Аттестация и КПК»

* **Тёмная тема**: кнопка 🌙/☀️ в шапке переключает светлое/тёмное оформление; выбор хранится
  в `localStorage` (`schoolhub-theme`) и применяется скриптом в `index.html` ещё до отрисовки
  React (без «вспышки» темы). Пока пользователь не переключал — тема следует настройке ОС
  (`prefers-color-scheme`). Вся палитра — CSS-переменные в `styles.css` (`:root[data-theme='dark']`),
  «бумага» документов и печатные формы остаются белыми.
* **Аттестация и КПК** (`certifications`): учёт сроков действия квалификационных категорий
  (`kind=CATEGORY`) и курсов повышения квалификации (`kind=CPK`: название, часы, учебное
  заведение) по каждому сотруднику; номер документа, даты присвоения/окончания, «действует до»
  (пусто = бессрочно), скан удостоверения/приказа в файловом хранилище, примечание.
* Доступы: Владелец/Администрация ведут раздел целиком, учитель видит только свои записи
  (capability `certifications:read` у всех, `certifications:manage` у администрации).
* Состояния записей вычисляются по дате: `valid / expiring (≤ CERT_REMINDER_DAYS, по умолчанию 60)
  / expired / indefinite`; фильтр и счётчики состояний в списке.
* **Напоминания** (общий фоновый цикл): сотруднику — персональное уведомление об истекающем/
  истёкшем сроке (дедупликация: не чаще одного в сутки по записи), администрации — ежедневная
  сводка после 9:00.
* **Массовый импорт/экспорт CSV** (UTF-8 BOM, разделитель «;» — открывается Excel напрямую):
  шаблон с примерами, импорт с разбором ошибок по строкам и сопоставлением сотрудников по ФИО
  (ё/регистр/пробелы игнорируются); повторная загрузка того же файла обновляет записи,
  а не плодит дубли (ключ: сотрудник + тип + название/категория + дата).
* Записи аттестации ищутся глобальным поиском (Ctrl+K) и попадают в журнал событий
  человекопонятными формулировками.

### 2.11 «Файлы школы», штрихкоды инвентаря и self-healing

* **«Файлы школы»** (Профиль → «Резервное копирование», только Владелец): дамп БД не содержит
  прикреплённые файлы, поэтому рядом с кнопкой дампа — сводка по файловому хранилищу (файлов на
  диске, объём, ссылок из базы, битые ссылки «запись есть — файла нет», файлы без записи в базе),
  «⬇ Скачать все файлы (ZIP)» — архив с исходными именами в папке `files/` плюс служебный
  `manifest.json` (пути хранилища, sha256), и «⬆ Загрузить архив с файлами» — идемпотентное
  восстановление: отсутствующие файлы возвращаются на свои пути, одинаковые не трогаются,
  отличающиеся заменяются версией из архива; окно-отчёт «восстановлено / заменено / уже на месте /
  сироты / ошибки». Архив без `manifest.json` отклоняется, пути из манифеста вне хранилища
  (zip-slip) отбрасываются поштучно.
* **Штрихкоды инвентаря**: у позиции поле `barcode` (EAN-13 / Code-128, уникальное), кнопка
  «📷 Сканировать» (камера: нативный BarcodeDetector, иначе вендорный `html5-qrcode`; аппаратный
  сканер работает как клавиатура — в поле поиска и в поле модалки), кнопка «🏷» печатает учётную
  этикетку (наименование, инв. №, штрихкод) как на бумажных этикетках школы; позициям без
  штрихкода предлагается служебный EAN-13 (префикс 200…) с присвоением в один клик.
  Глобальный поиск (Ctrl+K) ищет по штрихкоду, инвентарному и серийному номерам, а также по
  **номеру регистрации** входящих писем (в формате «77» и «77/2026») и по приказам о движении
  обучающихся.
* **Self-healing и автоочистка** (фоновый цикл, час): из `refresh_sessions` удаляются токены,
  истёкшие более месяца назад (`SESSION_PURGE_AFTER_DAYS`); если `audit_log` разрастается сверх
  `AUDIT_ARCHIVE_THRESHOLD` (300 000 строк), старые записи выгружаются в JSONL
  (`storage/audit_archive/`) и удаляются из БД, Владелец получает уведомление. Выключатель —
  `HOUSEKEEPING_ENABLED=false`.
* **Дни рождения**: необязательное поле карточки сотрудника + виджет на дашборде администрации
  («сегодня! / через N дн.»), ближайшие 30 дней.
* **Расписание**: пункт сайдбара «🕒 Расписание» открывает школьное расписание
  (raspisanie.nikasoft.ru) в новой вкладке.
* Исправлен баг тёмной темы: текст «бумажного» документа плана работы и печатных форм теперь
  всегда тёмный на белом листе (ранее наследовался светлый токен темы).

### 2.12 Закрепляемые виды списков и массовый редактор

* **«Запомнить этот вид»**: в списках «Приказы» и «Задачи» кнопка 📌 сохраняет текущие фильтры
  в профиле пользователя (`GET/PUT/DELETE /users/me/list-views/{key}`) — при следующем входе
  список открывается с этими фильтрами с любого устройства; кнопка «✖ Открепить» сбрасывает вид.
  Фильтры из ссылки (`?status=…` из поиска/уведомлений) приоритетнее закреплённых.
* **Массовый редактор сотрудников** (`POST /users/bulk-update`): галочки в списке пользователей →
  «✎ Изменить отмеченных» → разом добавить/убрать должности (например, «Руководитель ШМО») и
  (только Владелец) выдать/отозвать гранты модулей («Входящие», «Движение», «Инвентарь») или
  заблокировать/разблокировать. Недоступные по уровню роли учётки пропускаются с причиной,
  в журнал пишется одна запись `USER_BULK_UPDATE` со списком ФИО.
* **Визуальный конструктор дашборда**: кнопка «⠿ Раскладка» включает режим плиток — блоки
  (показатели, ознакомление и задачи, план недели, мои мероприятия, мой ВШК, последние
  приказы/задачи) перетаскиваются мышью, порядок сохраняется в профиле
  (`list-views/dashboard`) и восстанавливается при следующем входе; «✖ Сбросить порядок»
  возвращает раскладку по умолчанию.
* **WebSocket-уведомления**: каждая вкладка держит сокет `GET /api/v1/realtime/ws?token=…`
  (nginx-шаблон проксирует с Upgrade; ping/pong каждые 30 c, реконнект с бэкоффом); сервис
  уведомлений после записи в БД шлёт событие в сокеты пользователя — тост «Вам поставили
  новую задачу» появляется мгновенно, без перезагрузки; прежний поллинг счётчика (45 c)
  остаётся fallback'ом. Реестр соединений — в памяти процесса (в compose backend один worker).
* **Режим «Локдаун» (Lockdown)**: кнопка Владельца в профиле (и плашка-предупреждение в шапке)
  для экстренных случаев — демонстрация экрана, проверки, скриншоты. Пока включён, ФИО,
  телефоны, e-mail, логины, даты рождения и фото во всех разделах заменяются метками
  «Сотрудник N», «Ученик N», «Представитель N» (номер детерминирован: один человек — одна
  метка); Владелец видит настоящие данные. Маскируются и журнал событий, и глобальный поиск,
  и дашборд; редактирование персональных данных на это время отключено, чтобы маска не попала
  в БД. Включение/выключение пишется в журнал (`LOCKDOWN_ON`/`LOCKDOWN_OFF`).

### 2.13 Техподдержка школы, PDF-копия документа и резервный доступ Владельца

* **Helpdesk — заявки о неисправной технике.** Учитель сообщает «зажевало принтер»,
  «не включается компьютер», «нет интернета на интерактивной доске», «не работает
  документ-камера» — и обращение не теряется в мессенджере. Категории соответствуют
  реальной школьной технике (принтер/МФУ, компьютер, сеть, доска, проектор,
  документ-камера, звук, программы, доступы, телефон, прочее), у каждой своя иконка:
  очередь читается глазами.
  * **Жизненный цикл** — state machine на сервере (`app/enums.py::TICKET_TRANSITIONS`):
    `NEW → IN_PROGRESS → RESOLVED → CLOSED`, плюс `REJECTED` (с обязательной причиной)
    и `CANCELLED` (автор отозвал). Невозможный переход — 409.
  * **Очередь, а не назначение**: заявку видят все системные администраторы, и каждый
    берёт её в работу сам (`POST /helpdesk/{id}/take`). В школе сисадмин один-два,
    и «назначенная, но не взятая» заявка просто потерялась бы. Переназначение —
    тот же маршрут с `assignee_id` (уехал, заболел).
  * **Подтверждение автора**: «Выполнено» переводит заявку в `RESOLVED`, а закрывает
    её автор — «починили» должно означать «у учителя действительно работает».
    Кнопка «Не решено» возвращает заявку в работу. Молчит 5 дней
    (`TICKET_AUTOCLOSE_DAYS`) — закрывается сама с пометкой `auto_closed`.
  * **Норматив реакции, а не срок починки** (`TICKET_SLA_HOURS`): `URGENT` 2 ч,
    `HIGH` 4 ч, `NORMAL` 8 ч, `LOW` 24 ч. Норматив копируется в заявку при создании
    и пересчитывается при смене приоритета, поэтому правка справочника не переписывает
    историю. Просрочка подсвечивает строку журнала, есть в фильтрах и шлёт
    уведомление `TICKET_SLA_BREACH` (один раз на заявку).
  * **Кто сисадмин**: Владелец выдаёт грант `users.helpdesk_access` в карточке
    сотрудника → capability `helpdesk:manage`. `helpdesk:read` есть у всех ролей —
    подать заявку может любой. Массовая выдача гранта намеренно не сделана:
    роль привилегированная, назначают по одному.
  * Переписка (реплики + системные отметки одной лентой), вложения с фото поломки,
    KPI в шапке раздела, медиана времени реакции, экспорт CSV, глобальный поиск,
    уведомления с глубокими ссылками (`/helpdesk?t=<id>`) и бейдж очереди в меню.
* **PDF-копия документа.** Рядом с оригиналом автоматически создаётся PDF — и
  «Открыть» отдаёт копию в новой вкладке, а «Скачать» по-прежнему отдаёт оригинал.
  Работает для служебных записок, задач, инструкций и заявок техподдержки.
  Статус известен до загрузки (`document_pdf.plan_for(mime)`): `NA` / `PENDING` /
  `READY` / `FAILED` с причиной, понятной пользователю. Конвертация — LibreOffice
  headless (DOCX/XLSX/PPTX/ODT/RTF), ReportLab + Pillow (фото и текст, кириллический
  шрифт из `backend/assets/fonts`), всё фоново через `BackgroundTasks`; недоделанные
  копии доделываются при открытии карточки, поэтому `PENDING` не залипает навсегда.
  Единый вид вложений во всех разделах — компонент `frontend/src/components/DocLink.tsx`.
* **Печатный бланк служебной записки** (`app/services/note_print.py`): шапка школы,
  адресат в дательном падеже, номер и дата, тема, текст, перечень приложений,
  реквизиты, подпись автора, виза «СОГЛАСОВАНО» (способ подписи, дата, место для
  печати), отметка об исполнении, колонтитул; `?auto_print=true` сразу открывает
  диалог печати. Все пользовательские значения экранируются, CSP отдаётся метатегом
  и заголовком: форму открывает согласующий, а текст пишет любой сотрудник.
  При утверждении записки её документы **дублируются** в задачу исполнителю
  (`storage.duplicate` + копия PDF) — жизненные циклы независимы, удаление файла
  из записки не ломает задачу.
* **Инструкции с несколькими документами.** У статьи справки теперь несколько
  вложений с подписями («Приложение 1», «Бланк заявления») — таблица
  `help_article_files`; одиночные файлы из старой колонки перенесены миграцией.
  Документы открываются в новой вкладке, а не во всплывающем окне. Устаревшие
  маршруты `POST/GET /help/{id}/file` сохранены для совместимости.
* **Резервный доступ Владельца (break-glass).** Если устройство с аутентификатором
  утрачено, подписывать нечем — а восстановлением из копии и выходом из локдауна
  управляет именно подпись. `POST /users/me/totp/break-glass` (**только Владелец**)
  заменяет её парой факторов, которые Владелец знает: локальный пароль + контрольное
  слово, заданное заранее. Подбор троттлится отдельным лимитером
  (`BREAK_GLASS_MAX_ATTEMPTS` / `BREAK_GLASS_WINDOW_MIN`), каждая неудача пишется в
  журнал отдельной транзакцией, после успеха отзываются **все** сессии Владельца,
  cookie снимается, администрация получает уведомление.

**Слои backend'а** (зависимости направлены внутрь, бизнес-логика не знает про HTTP):

```
app/
├── api/          # HTTP-слой: маршруты, RBAC-зависимости, сериализация ответов
├── services/     # бизнес-логика: приказы, задачи, уведомления, аудит, хранилище, документы
├── models/       # SQLAlchemy ORM (таблицы и связи)
├── schemas/      # Pydantic-контракты запросов/ответов
├── security.py   # JWT, хеширование паролей, require_role(), get_current_user
├── capabilities.py  # матрица прав «роль → возможности» (единый источник для API и UI)
├── enums.py      # доменные справочники и state machine статусов
├── types.py      # портируемые типы колонок (UUID, Enum→VARCHAR)
├── dbutils.py    # переносимый регистронезависимый поиск (ILIKE ↔ SQLite)
└── main.py       # фабрика приложения, middleware, обработчики ошибок
```

Подробности — в [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) (модель данных, ключевые решения, ADR).
Полный контракт API — в [`docs/API.md`](docs/API.md) и в Swagger (`/docs`).

## 7. Продуктивный контур (чек-лист)

1. **Секреты и периметр**: `APP_ENV=prod` (отключает `/docs` и `/openapi.json`),
   `SECRET_KEY` из vault/secret-manager **или** автогенерация в файле `SECRET_KEY_FILE`
   (том `secrets_v2`, права 0600) — захардкоженных ключей в репозитории нет.
   `CORS_ORIGINS` перечисляет адреса явно: значение `*` вместе с `allow_credentials=True`
   открыло бы API любому сайту, поэтому «звёздочка» игнорируется с записью в журнал.
   Файл `backend/storage/secret_key` не должен попадать в репозиторий (закрыт `.gitignore`);
   если ключ когда-либо утекал — удалите его (или том `secrets`) и перезапустите backend:
   новый ключ сгенерируется автоматически, все сессии будут сброшены.
2. **Миграции**: схему приводит в актуальное состояние `init_db()` при старте (`AUTO_MIGRATE=true`):
   `alembic upgrade head` (`backend/alembic/`) + идемпотентные шаги `backend/app/migrations.py`.
   Новая колонка/индекс вносится в **обе ветки**: ревизия alembic и шаг `_mNNN_*` в
   `backend/app/migrations.py` (`docs/DEV-GUIDE.md` §4.6). Ручной прогон: `alembic upgrade head`.
   Подробности и защита от дрейфа схемы — `docs/ARCHITECTURE.md`, ADR-14.
3. **Хранилище**: заменить `LocalFileStorage` на S3/MinIO (протокол `FileStorage` уже описан),
   bucket приватный, раздача через подписанные URL.
4. **HTTPS**: TLS-терминация на nginx/ingress, `Strict-Transport-Security`; включите
   `COOKIE_SECURE=true` (cookie начнёт передаваться только по HTTPS).
5. **Refresh-токены**: уже httpOnly + `SameSite=strict` + серверные сессии с ротацией и отзывом;
   при горизонтальном масштабировании deny-list не нужен — сессии лежат в PostgreSQL.
6. **Лимиты**: rate-limit на `/auth/login` встроен (попытки/минуту на IP+логин), неудачные попытки в аудите.
7. **Наблюдаемость**: structured-логи (JSON), `/health` и `/api/v1/health` уже есть —
   добавьте отдельный `/ready` (проверка БД и хранилища), метрики Prometheus, трейсинг (OpenTelemetry).
8. **Резервные копии**: ежедневный `pg_dump` + снапшоты хранилища документов; проверка восстановления.
9. **Превью DOCX**: конвертер `libreoffice-writer-nogui` уже включён в образ
   (`backend/Dockerfile`); PDF для инлайн-просмотра генерируется фоном при загрузке
   документа и кэшируется рядом с файлом (`app/services/documents.py`).
10. **CI**: `pytest`, `smoke_test.py`, `tsc --noEmit`, `npm run build`, линтеры (ruff/eslint), scan образов (trivy).

## 8. Что расширено сверх ТЗ

* Авторизация через Active Directory: LDAP/LDAPS bind, авто-провижининг учётных записей,
  синхронизация атрибутов и групп, маппинг групп на роли, импорт сотрудников из каталога,
  панель диагностики подключения к DC.
* Готовый комплект развёртывания на Synology NAS (arm64): compose с лимитами памяти,
  скрипт подготовки домена (PowerShell), ежедневный `pg_dump` с ротацией и контрольными
  суммами, скрипт диагностики, конфигурация DSM Reverse Proxy.

* Уведомления (in-app) о новых приказах, назначении задач, смене статусов и комментариях.
* Журнал событий с человекопонятными формулировками (фраза «что сделано» + строки деталей вместо сырых diff/uuid) и выгрузка листа ознакомления в CSV.
* Версионирование документов, sha256-контроль целостности, история статусов задачи.
* Дашборд с ролевой семантикой (личный контур у учителя, глобальный у администрации).
* Канбан-доска задач, отчёт по просрочкам, справочники и матрица прав через API.
