ШКОЛА HUB — ОБНОВЛЕНИЕ РАБОЧЕЙ МАШИНЫ (SYNOLOGY): СНАЧАЛА КОПИЯ, ПОТОМ ОБНОВЛЕНИЕ
=================================================================================
Редакция от 29.10.2026. Обновление до версии 1.12.0.

Инструкция написана для машины, на которой последняя установка была «по ВШК»
(модуль внутришкольного контроля), то есть ДО версий:
    • 1.7.0 — электронная подпись (ПЭП), служебные записки, замещения, справка/FAQ;
    • 1.8.0 — безопасность по итогам ревью, видимость статей справки, «Файлы школы»;
    • 1.9.0 — второй проход по безопасности, аварийный сброс аутентификатора;
    • 1.10.0 — история повторяющихся задач («пропущено» за каждый период),
      точные подписи сроков, переменные для HTTPS за реверс-прокси DSM;
    • 1.11.0 — служебные записки: каждый видит только своё (Владелец выдаёт
      грант «Все служебные записки»), удаление и печать записок, видимый
      согласующий; замещения: задачи передаются только после подтверждения
      замещающим и возвращаются при отмене/завершении/удалении, появилось
      продление периода, строки удаляют Владелец и кадровик (грант «Кадровик:
      замещения»); тип подписи приказа выбирается в форме; файлы инструкций
      открываются во всплывающем окне; QR-код для привязки аутентификатора;
      приветствие по имени; выход на экран входа после 3 часов неактивности;
    • 1.12.0 — техподдержка школы (заявки о неисправной технике: очередь,
      норматив реакции, подтверждение автора, автозакрытие); резервный сброс
      аутентификатора Владельца без телефона (пароль + контрольное слово);
      автоматическая PDF-копия документа — Word, Excel, PowerPoint и фото
      открываются кликом в новой вкладке, оригинал остаётся на скачивание;
      служебная записка печатается на бланке с визой согласования, а её
      документы передаются вместе с задачей исполнителю; у инструкции теперь
      несколько документов с подписями («Приложение 1», «Бланк заявления»).
Переход выполняется СРАЗУ через несколько версий — это штатный сценарий: схема базы
приводится в актуальное состояние автоматически при старте контейнера, ничего
вручную накатывать не нужно.

ГЛАВНОЕ ПРАВИЛО

Копия, которую ни разу не пробовали восстановить, копией не является: в ШАГЕ 1.5

ЧТО ОБНОВЛЕНИЕ ДЕЛАЕТ И ЧЕГО НЕ ДЕЛАЕТ
--------------------------------------
Заменяется:      исходный код (папки backend/ и frontend/) и образы контейнеров.
НЕ трогается:    база данных (том db_v2), вложения и документы (том uploads_v2),
                 ключ сессий (том secrets_v2), ваши настройки в .env.
Схема базы:      недостающие шаги применяются сами при первом старте
                 (AUTO_MIGRATE=true) — в журнале backend будут строки «migrations: …».
Данные:          не удаляются и не переписываются. Новые модули просто добавят
                 свои таблицы и колонки.

-------------------------------------------------------------------------------
1.1  ДАМП БАЗЫ ДАННЫХ (самое важное: пользователи, приказы, задачи, планы,
     ознакомления, журнал событий)
-------------------------------------------------------------------------------
ВАРИАНТ А — через веб-интерфейс, без SSH (работает и на старой версии):
    1. Войдите под Владельцем: http://<адрес-NAS>:8080
    2. Аватар справа вверху → «Мой профиль» → раздел «Резервное копирование».
    3. Нажмите «⬇ Скачать резервную копию БД».
       В старой версии подпись не требуется; в 1.9.0 кнопка попросит
       «код + слово» (см. ШАГ 7 — привяжите аутентификатор сразу).
    4. Файл schoolhub-backup-<дата>.sql скачается на компьютер.
    5. File Station → откройте папку backup/schoolhub/update-20261028 →
       «Загрузить» → выберите скачанный .sql. Дождитесь окончания загрузки.
    6. НЕ ЗАКРЫВАЙТЕ вкладку и не выключайте NAS, пока загрузка не завершится.

ВАРИАНТ Б — по SSH (быстрее и сразу кладёт файл на NAS, минуя компьютер):
    ssh <ваш-пользователь>@<адрес-NAS>
    sudo -i
    mkdir -p /volume1/backup/schoolhub/update-20261028
    cd /volume1/backup/schoolhub/update-20261028
    docker exec -i schoolhub-db pg_dump -U schoolhub -d schoolhub \
        --no-owner --clean --if-exists > db-before-update.sql
    gzip -6 db-before-update.sql
    sha256sum db-before-update.sql.gz > db-before-update.sql.gz.sha256
    ls -lh

    Если на NAS уже настроен планировщик с deploy/synology/backup-db.sh — можно
    просто запустить его вручную: DSM → Панель управления → Планировщик задач →
    выбрать задачу «SchoolHub backup» → «Запустить» (дамп появится в
    /volume1/backup/schoolhub/). Для обновления всё равно сделайте отдельную
    копию в папке update-<дата>: её не затронет ротация старых дампов.

-------------------------------------------------------------------------------
1.2  ФАЙЛЫ И ВЛОЖЕНИЯ (документы приказов, вложения задач, аватары, сканы)
-------------------------------------------------------------------------------
Обновление этот том НЕ изменяет, но копия нужна: при откате или сбое диска
восстанавливать придётся и файлы.

ВАРИАНТ А — по SSH (рекомендуется, 2–10 минут):
    cd /volume1/backup/schoolhub/update-20261028
    docker run --rm \
        -v schoolhub_uploads_v2:/data:ro \
        -v /volume1/backup/schoolhub/update-20261028:/backup \
        alpine tar -czf /backup/uploads-before-update.tar.gz -C /data .
    sha256sum uploads-before-update.tar.gz > uploads-before-update.tar.gz.sha256

    Имя тома уточните:  docker volume ls | grep uploads
    (у проекта schoolhub оно обычно schoolhub_uploads_v2).

ВАРИАНТ Б — без SSH, временным контейнером (только веб-интерфейс DSM):
    1. Container Manager → «Реестр» → найдите образ alpine → «Загрузить» (latest).
    2. Container Manager → «Образ» → alpine → «Запустить» → «Дополнительные настройки»:
       • «Тома» → «Добавить»:
             /volume1/backup/schoolhub/update-20261028  →  /backup   (снять «только чтение» нельзя, это запись)
         том docker-тома uploads_v2                      →  /data    (поставить «Только чтение»)
         (том выбирается из списка: schoolhub_uploads_v2)
       • В мастере уберите галочку «Включить автоматический перезапуск».
    3. В поле «Команда» (или в настройках контейнера → «Команда») укажите:
             sh -c "tar -czf /backup/uploads-before-update.tar.gz -C /data . && echo DONE"
    4. Запустите и смотрите журнал контейнера: последняя строка DONE — файл готов.
    5. Контейнер удалите (он одноразовый).

ВАРИАНТ В — штатные средства NAS: если папка с томами входит в задачу
    Hyper Backup или Snapshot Replication, запустите копию вручную и дождитесь
    окончания. Том Docker лежит в /var/lib/docker/volumes/… — в обычные задачи
    Hyper Backup он попадает не всегда, поэтому варианты А/Б надёжнее.

1.3  КОНФИГУРАЦИЯ И СЕКРЕТЫ (без них откат вернёт систему с сброшенными сессиями)
-------------------------------------------------------------------------------
ВАРИАНТ А — через File Station (без SSH):
    Скопируйте в папку копии из папки проекта (/volume2/docker/schoolhub/app):
        docker-compose.yml
        .env                     (если он есть; в нём пароли — никому не пересылайте)
        УСТАНОВКА.txt            (та редакция, по которой ставили систему)
    Копирование: ПКМ по файлу → «Копировать в…» → выбрать папку копии.

ВАРИАНТ Б — по SSH (плюс ключ сессий из тома secrets_v2):
    cd /volume1/backup/schoolhub/update-20261028
    cp /volume2/docker/schoolhub/app/docker-compose.yml ./docker-compose.yml.before
    [ -f /volume2/docker/schoolhub/app/.env ] && \
        cp /volume2/docker/schoolhub/app/.env ./env.before
    docker run --rm -v schoolhub_secrets_v2:/data:ro \
        -v /volume1/backup/schoolhub/update-20261028:/backup \
        alpine sh -c "cp /data/secret_key /backup/secret_key.before && chmod 600 /backup/secret_key.before"

    secret_key.before — это ключ подписи сессий. Положите его в папку, куда нет
    доступа никому, кроме администратора: с ним можно подделать токен любого
    пользователя. В репозиторий, в почту и в мессенджеры — НЕ отправлять.

1.5  ПРОВЕРКА КОПИИ — ОБЯЗАТЕЛЬНО
-------------------------------------------------------------------------------
Проверяем, что копии вообще читаются. Пять минут, которые спасают от «а дамп-то
пустой».

По SSH:
    cd /volume1/backup/schoolhub/update-20261028
    ls -lh                                  # размеры не нулевые
    sha256sum -c db-before-update.sql.gz.sha256        # «OK»
    gunzip -c db-before-update.sql.gz | head -20       # виден текст SQL
    gunzip -c db-before-update.sql.gz | grep -c "CREATE TABLE"   # больше 20
    tar -tzf uploads-before-update.tar.gz | head -5    # список файлов читается
    tar -tzf uploads-before-update.tar.gz | wc -l      # число файлов > 0

Без SSH (File Station):
    • размеры файлов видны в списке и не равны 0;
    • .sql открывается на просмотр (ПКМ → «Открыть» → текстовый редактор) и
      начинается с комментариев pg_dump и команд CREATE TABLE;
    • .tar.gz можно «Извлечь» во временную папку — если распаковалось, архив цел.

Дополнительно (самая надёжная проверка, если есть свободное время):
    восстановите дамп в тестовую базу и убедитесь, что система открывается.
    См. «ПРОВЕРКА КОПИИ НА ТЕСТОВОМ КОНТЕЙНЕРЕ» в конце файла.

1.6  УНЕСТИ КОПИЮ С МАШИНЫ
-------------------------------------------------------------------------------
Папка копии лежит на том же NAS, что и система. Добавьте ещё один рубеж:
    • скопируйте папку на внешний USB-диск, подключённый к NAS
      (File Station → USB-диск → «Копировать в…»), ИЛИ
    • включите папку /volume1/backup/schoolhub в задачу Hyper Backup

    • скачайте дамп базы и архив файлов на рабочий компьютер и уберите в сейф/облако.
Минимум, который должен получиться: одна копия на NAS + одна копия вне NAS.

ШАГ 4. ПРОВЕРИТЬ docker-compose.yml И .env
===============================================================================
ВНИМАНИЕ: в отличие от обновления 1.7.0, здесь compose-файл ЗАМЕНИТЬ НУЖНО.
В старой редакции (машина «по ВШК») ключ подписи сессий SECRET_KEY был вписан прямо
в файл — а репозиторий публичный, значит ключ известен всем. В новой редакции
секретов в файлах нет: ключ берётся из тома secrets_v2.

1. Сравните файл из архива с тем, что лежал у вас (копия docker-compose.yml.before).
   Возьмите НОВЫЙ docker-compose.yml из архива, но перенесите в него свои значения:
        • APP_ROOT / пути сборки (build.context) — если проект лежит не в
          /volume2/docker/schoolhub/app;
        • HTTP_PORT — если сайт открывается не на 8080;
        • POSTGRES_PASSWORD — если задавали свой;
        • TZ, LDAP_* — если включали домен.
   Проще всего: открыть оба файла в текстовом редакторе и перенести строки с
   вашими значениями в новый файл.

2. Рядом с docker-compose.yml создайте/проверьте файл .env (образец —
   .env.example в архиве). Минимально:
        APP_ROOT=/volume2/docker/schoolhub/app
        HTTP_PORT=8080
        POSTGRES_PASSWORD=<ваш пароль, если он не «schoolhub»>
        TZ=Europe/Moscow
        AUTO_MIGRATE=true
   Новые необязательные переменные 1.9.0 (можно не задавать — значения по
   умолчанию безопасны): APP_ENV=prod, CORS_ORIGINS=[], TOTP_MAX_ATTEMPTS=5,
   TOTP_LOCK_WINDOW_MIN=15, FILES_ARCHIVE_MAX_MB=512,
   FILES_ARCHIVE_UNPACKED_MAX_MB=4096, DOC_CONVERT_TIMEOUT_SEC=60.
   Новые необязательные переменные 1.12.0 (тоже с безопасными значениями по
   умолчанию): TICKET_AUTOCLOSE_DAYS=5 — через сколько дней молчания автора
   заявка техподдержки закрывается сама; BREAK_GLASS_MAX_ATTEMPTS=5 и
   BREAK_GLASS_WINDOW_MIN=30 — лимит подбора пароля и контрольного слова при
   резервном сбросе аутентификатора Владельца; DOC_CONVERT_TIMEOUT_SEC — теперь
   общий таймаут конвертации любого офисного документа в PDF-копию (на DS223
   при ошибках «PDF-копию сделать не удалось: превышен таймаут» поднимите
   до 120–180).

   Если включили HTTPS через реверс-прокси DSM (актуально с 1.10.0 — compose
   начал пробрасывать CORS_ORIGINS в контейнер backend), добавьте в .env:
        TRUST_PROXY_HEADERS=true
        COOKIE_SECURE=true
        CORS_ORIGINS=["https://atom-school.local:9090"]
   В CORS_ORIGINS укажите адрес, по которому пользователи открывают систему
   (со схемой https:// и портом, если он есть). Формат — JSON-список или
   перечисление через запятую без скобок. После правки .env пересоздайте
   контейнеры:  docker compose up -d  (пересборка образов не требуется).

3. Проверьте тома — они должны остаться прежними (иначе данные «исчезнут»):
        db_v2, uploads_v2, secrets_v2
   В новом compose имена те же, что и у вашей установки; менять их НЕЛЬЗЯ.

ЧТО БУДЕТ С СЕССИЯМИ ПОСЛЕ ОБНОВЛЕНИЯ
-------------------------------------
Раньше SECRET_KEY брался из compose (публично известный), теперь — из файла
в томе secrets_v2. Если файла там нет, ключ сгенерируется заново, поэтому
ВСЕМ пользователям придётся войти заново. Это ожидаемо и безопасно.
Если хотите сохранить прежний ключ (например, чтобы не выгонять всех), положите
его в том secrets_v2 файлом secret_key (права 600) — он у вас есть в копии
secret_key.before. НО: ключ из старой редакции compose считается скомпрометированным,
поэтому рекомендуемый путь — позволить системе сгенерировать новый.

⚠️ Если бы вы обновлялись с версий 1.7.0/1.8.0, где сотрудники уже привязали
аутентификаторы (ПЭП), смена SECRET_KEY сделала бы эти привязки нечитаемыми:
их пришлось бы сбросить (кнопка «Сбросить аутентификатор» в карточке сотрудника)
и привязать заново. На машине «по ВШК» привязок ещё нет — замена ключа ничем
не грозит.


===============================================================================
ШАГ 5. ПЕРЕСОБРАТЬ И ЗАПУСТИТЬ
===============================================================================
Container Manager → «Проект» → schoolhub → «Пересобрать» (Rebuild).
Дождитесь окончания сборки обоих образов (backend: python-зависимости,
frontend: npm ci + vite + nginx). На DS223 это самая долгая часть — 10–20 минут.
Затем проект запустится сам (или нажмите «Запустить»).

По SSH:
    cd /volume2/docker/schoolhub/app
    docker compose build --no-cache
    docker compose up -d
    docker compose logs -f backend        # Ctrl+C — выйти из просмотра журнала

Что должно быть в журнале schoolhub-backend (Container Manager → Контейнер →
schoolhub-backend → «Журнал»):
    migrations: users.totp_enabled добавлена            ← шаги m013…m022
    migrations: таблица service_notes создана
    migrations: таблица substitutions создана
    migrations: таблица help_articles создана
    migrations: help_articles.visibility добавлена
    SECRET_KEY сгенерирован автоматически и сохранён: /data/secrets/secret_key
    Application startup complete
Строки «migrations: …» появляются только один раз — при первом старте после
обновления (дальше шагам нечего менять). Отсутствие ошибок и наличие
«Application startup complete» — главный признак успеха.

Если в журнале ошибка — НЕ начинайте править базу руками. Переходите к разделу
«ОТКАТ», а журнал сохраните (кнопка «Загрузить журнал» или `docker logs
schoolhub-backend > log.txt` по SSH) — он понадобится, чтобы разобраться.

   «Справка» (у учителя — только разрешённые ему статьи), «Уведомления»

5. Профиль Владельца → «Файлы школы»: сводка показывает файлы на диске и

6. Журнал событий (Профиль → «Журнал»): видны записи о входе и о применении
   миграций; старых записей не стало меньше.
7. WebSocket/колокольчик: создайте задачу на себя — уведомление появляется без

   это не ошибка; см. dsm-reverse-proxy.conf про заголовки Upgrade).
8. Повторяющиеся задачи (1.10.0): создайте задачу «каждый день», отметьте
   выполнение — в карточке появится блок «История повторений» с периодом
   «выполнено». Если период истечёт невыполненным, к утру в истории появится
   «пропущено», а в списке задач — бейдж «⚠ пропущено N периодов».
9. Служебные записки (1.11.0): войдите учителем — в журнале только его записки;
   войдите администратором без гранта — только записки, где он согласующий
   (и записки без назначенного согласующего). В карточке сотрудника (Пользователи
   → «Права доступа») появился переключатель «Все служебные записки». Создайте
   записку с согласующим, утвердите её кодом — в журнале и в печатной форме видно,
   КТО согласовал. Кнопка «Печать» открывает форму в новой вкладке (без ошибки 401).
   Владелец может удалить любую записку, включая утверждённую.
10. Замещения (1.11.0) — проверьте по шагам:
       • оформите замещение с галочкой «активные задачи»: сразу после создания
         задача остаётся у ОТСУТСТВУЮЩЕГО, а в журнале написано «передастся после
         подтверждения»;
       • войдите замещающим — у него в меню появился пункт «Замещения» (только на
         время его замещения), в журнале видна лишь его строка; нажмите
         «Подтвердить» — задача перешла к нему, в журнале «передано <дата и время>»;
       • нажмите «Отменить» (или «Завершить») — задача ВЕРНУЛАСЬ отсутствующему,
         в журнале «возвращено отсутствующему»;
       • «Продлить» — сдвигает дату окончания (больничный продлили), объекты не
         трогает, участники получают уведомление;
       • «Удалить» видна только Владельцу и кадровику. Кадровика назначает Владелец:
         Пользователи → карточка сотрудника → «Права доступа» → «Кадровик:
         замещения» (должность значения не имеет — хоть классный руководитель,
         хоть руководитель ШМО). Администрация без гранта строки не удаляет;
       • у учителя, который не участвует в замещениях, пункта «Замещения» в меню
         нет, а CSV-экспорт журнала недоступен;
       • кнопки в строках журнала стоят ровно (раньше «Завершить/Отменить» уезжали).
11. Приказы (1.11.0): в форме приказа — селектор «Подпись ознакомления»
    (без подписи / клик / код / код+слово); у приказов о движении обучающихся
    слабее «кода» не даст выбрать сервер.
12. Справка (1.12.0): карточки инструкций выровнены в аккуратную сетку; у статьи
    с документами — значок «📎 N файла(ов)». В самой статье блок «Документы»:
    каждое вложение со своей подписью («Приложение 1», «Бланк заявления»),
    кнопками «Открыть» и «Скачать». «Открыть» запускает документ В НОВОЙ

    как PDF, потому что сервер сам делает копию. Администрация может приложить

13. Навигация и приветствие (1.11.0): из левого меню исчезли «Уведомления»

    браузера; проверка срабатывает и сразу при открытии страницы (вернулись
    к компьютеру через сутки — придётся войти заново).

16. Техподдержка (1.12.0) — проверьте по шагам:
       • войдите УЧИТЕЛЕМ: в меню пункт «Техподдержка», внутри — только его
         собственные заявки и кнопка «+ Подать заявку». Создайте заявку

         кабинет 214, приложите фото — заявка получила номер (№1/2026);
       • войдите ВЛАДЕЛЬЦЕМ: в журнале видна та же заявка, у неё статус «Новая»,
         в строке — норматив реакции (для «Обычного» приоритета 8 ч) и кнопка
         «Взять в работу». Нажмите её — статус «В работе», исполнитель — вы,

         описанием работ — статус «Выполнена»;
       • войдите АВТОРОМ (тем же учителем): он видит вашу работу и две кнопки —

         заявка вернулась в работу; затем «Выполнено» → «Работает, закрыть» —

       • «Экспорт CSV» выгружает журнал заявок (у учителя кнопки нет).
17. Кто системный администратор (1.12.0): Пользователи → карточка сотрудника →
    «Статус и доступы» → переключатель «Системный администратор (техподдержка)».
    С грантом человек видит всю очередь и может брать заявки в работу; без гранта —
    только свои обращения. Владелец в очереди всегда, грант ему не нужен.
    Назначьте хотя бы одного сисадмина, иначе заявки будет видеть только Владелец.
18. PDF-копия документа (1.12.0): приложите к служебной записке или к задаче
    файл Word — у вложения сначала подпись «PDF-копия готовится», через
    несколько секунд кнопка «Открыть» показывает документ в новой вкладке.
    Кнопка «Скачать» по-прежнему отдаёт ОРИГИНАЛ (Word), копия его не заменяет.
    То же работает для Excel, PowerPoint, фото и текстовых файлов.
    Если вместо «Открыть» написано «PDF-копию сделать не удалось» — в образе
    не хватает конвертера (см. ЧАСТЫЕ ПРОБЛЕМЫ).
19. Печать служебной записки (1.12.0): кнопка «Печать» открывает бланк А4 —
    шапка школы, адресат, номер и дата, тема, текст, перечень приложений,
    подпись автора, блок «СОГЛАСОВАНО» со способом подписи и датой и место
    для печати, отметка об исполнении. Диалог печати открывается сам

20. Резервный доступ Владельца (1.12.0): Профиль → «Резервный доступ (потеря

    пока контрольное слово не задано (блок «Электронная подпись (ПЭП)» выше).
    Проверять сброс на рабочей машине не нужно — достаточно убедиться, что
    блок виден, а бейдж показывает «Контрольное слово задано».

7.5  НАЗНАЧИТЬ СИСТЕМНЫХ АДМИНИСТРАТОРОВ ТЕХПОДДЕРЖКИ (новое в 1.12.0).

7.6  ЗАПИСАТЬ КОНТРОЛЬНОЕ СЛОВО ВЛАДЕЛЬЦА (новое в 1.12.0 — проверить, что задано).

ОТКАТ (если что-то пошло не так)
===============================================================================
Случай 1. Новая сборка не стартует или ведёт себя неверно, ДАННЫЕ НЕ ПОСТРАДАЛИ
(миграции не успели примениться, либо применились частично и система не работает).
Обычно этого достаточно:
    1. Container Manager → «Проект» → schoolhub → «Остановить».
    2. File Station: удалите новые backend и frontend; переименуйте обратно
           backend.old-20261028  →  backend
           frontend.old-20261028 →  frontend
       Верните прежний docker-compose.yml (из копии docker-compose.yml.before).
    3. Container Manager → «Пересобрать» → «Запустить».
    4. Проверьте прежнюю версию в /api/v1/health.
    Примечание: шаги миграций, которые успели примениться, назад не откатываются —
    они только ДОБАВЛЯЮТ таблицы/колонки и старой версии не мешают.

Случай 2. База повреждена или данные пропали — восстанавливаем из копии:
    1. Container Manager → «Проект» → «Остановить».
    2. Верните старый код и compose (как в случае 1).
    3. Восстановите базу:
       по SSH:
            cd /volume2/docker/schoolhub/app
            docker compose start db
            sudo bash deploy/synology/restore-db.sh \
                /volume1/backup/schoolhub/update-20261028/db-before-update.sql
            (скрипт сам сделает свежую копию «на всякий случай» и сбросит схему;
             если дамп в .gz — сначала gunzip)
       или запустите проект и в интерфейсе Владельца:
            Профиль → «Резервное копирование» → «Восстановить из копии» →
            выберите .sql-файл. В старой версии подпись не требуется;
            в 1.9.0 — нужна подпись «код + слово».
    4. Файлы (если их тоже возвращаем):
            docker run --rm -v schoolhub_uploads_v2:/data \
                -v /volume1/backup/schoolhub/update-20261028:/backup \
                alpine sh -c "cd /data && tar -xzf /backup/uploads-before-update.tar.gz"
    5. Container Manager → «Пересобрать» → «Запустить» → проверка по ШАГУ 6.

Случай 3. Не запускается контейнер db (редко; обычно из-за нехватки места):
    проверьте свободное место на томе и journal; при сомнении — восстановите
    дамп в новый том, НЕ удаляя старый. Напишите в поддержку, приложив журнал.

ЧАСТЫЕ ПРОБЛЕМЫ
===============================================================================
• Сайт не открывается после пересборки.
  Container Manager → контейнеры: все три должны быть «Выполняется» и «Исправно».
  Смотрите журнал backend'а. Частая причина — ошибка в docker-compose.yml после
  переноса своих значений (путь APP_ROOT, порт).

• В журнале «relation … does not exist» или «column … does not exist».
  Миграции не доехали: убедитесь, что в compose/`.env` стоит AUTO_MIGRATE=true,
  и перезапустите проект. Если ошибка осталась — откат (Случай 1) и журнал
  в поддержку.

• Все пользователи «вылетели» и просят войти заново.
  Ожидаемо: сменился ключ подписи сессий (см. ШАГ 4). Пароли не менялись.

• Кнопка «Скачать резервную копию БД» просит код и слово.
  Так работает 1.8.0+: выгрузка всех персональных данных — только по подписи.
  Привяжите аутентификатор (ШАГ 7.1). Если телефон потерян — попросите второго
  Владельца или восстановите копию по SSH (backup-db.sh).

• Кнопка «🗑 Удалить» в справочнике сотрудников открывает окно подписи.
  Это правильно: удаление учётки — операция «код + слово». До 1.9.0 кнопка
  просто выдавала ошибку 409.

• При импорте инвентаря часть строк отклонена с причиной про штрихкод.
  С 1.9.0 в поле «Штрихкод» допускаются только символы, которые выдаёт сканер
  (цифры, латиница, знаки . _ : / + - # * ( )). Кириллица и «острые» символы
  отклоняются: значение попадает в SVG этикетки. Поправьте значения в файле и
  загрузите его заново — импорт идемпотентен.

• В Excel/Calc ячейки выгрузок начинаются с апострофа (').
  Это защита от формульных инъекций: апостроф виден в строке формул, но не
  печатается, и значение не исполняется как формула. Удалять его не нужно.

• Пересборка падает на npm/vite или не хватает памяти.
  На DS223 (512 МБ–2 ГБ ОЗУ) сборка frontend'а тяжёлая: остановите другие
  контейнеры и пакеты (например, антивирус/индексацию) на время сборки,
  повторите «Пересобрать».

• После обновления пропали вложения приказов.
  Не могут: файлы лежат в томе uploads_v2, обновление его не трогает. Проверьте,
  что в compose том смонтирован (uploads_v2:/data/uploads) и что UPLOAD_DIR
  не изменился. Профиль → «Файлы школы» покажет, сколько файлов на диске.

• У документа написано «PDF-копию сделать не удалось» (нет конвертера).
  С 1.12.0 PDF-копия создаётся для Word, Excel, PowerPoint и ODF. В образ
  добавлены пакеты libreoffice-writer-nogui, libreoffice-calc-nogui и
  libreoffice-impress-nogui. Если пересборка шла из старого кэша — выполните
  «Пересобрать» ещё раз (Container Manager → проект → Пересобрать) и проверьте
  внутри контейнера:  docker compose exec backend which soffice
  Оригинал файла при этом НЕ теряется: кнопка «Скачать» работает всегда.

• Фото и сканы не открываются в новой вкладке.
  Для изображений PDF-копию собирает ReportLab с Pillow; если пакет не
  установился, пересоберите образ. Проверка внутри контейнера:
      docker compose exec backend python -c "import PIL, reportlab; print('ok')"

• Заявки техподдержки видит только Владелец.
  Так и задумано: очередь доступна Владельцу и сотрудникам с грантом
  «Системный администратор (техподдержка)». Назначьте сисадминов (ШАГ 7.5).
  Учителя при этом подают заявки и видят свои обращения — грант им не нужен.

• Владелец потерял телефон с аутентификатором.
  Профиль → «Резервный доступ (потеря устройства)» → «🚨 Сбросить
  аутентификатор без телефона» → локальный пароль + контрольное слово.
  Все сессии Владельца закроются, администрация получит уведомление,
  действие останется в журнале. Если контрольное слово не задавали —
  доступ возвращает только второй Владелец (или правка базы по SSH).
  После нескольких неудачных попыток процедура блокируется на 30 минут.

• WebSocket-уведомления не приходят мгновенно.
  В dsm-reverse-proxy.conf должны быть заголовки Upgrade/Connection для порта 8080
  (файл в deploy/synology/). Без них система работает на поллинге раз в 45 секунд —
  функциональность не теряется.
